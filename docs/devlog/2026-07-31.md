# 2026-07-31 ngplan Development Log

## Work Summary

잘못된 반월 기간으로 계획을 시작한 뒤 기간을 고치는 과정에서 기존 날짜별 수동 입력이 사라진 실사용 사고를 기준으로, 시작 기간 확인과 제한된 복구 보관 체계를 추가했다. 셀 수정마다 무한한 버전을 만드는 대신 짧은 간격의 순환 보관, 중요 작업 직전 보관, 기존 하루 보관을 조합하고 복구 시 원본을 덮어쓰지 않도록 했다.

## Work Completed

- 새 계획을 열기 전에 연·월·상하반기와 실제 날짜 범위를 확인하는 대화상자를 추가하고 상파울루 업무 날짜 기준 다음 반월을 추천하도록 했다.
- 기간 편집 중에는 임시 초안만 바뀌게 하고, 수동 계획표가 한 번이라도 생성된 뒤 기간을 바꾸면 기존 계획을 수정하지 않고 새 기간 사본을 만들도록 했다. 기간이 다른 사본에는 날짜별 수동 셀을 옮기지 않는다.
- 15분 슬롯 기준 최근 7일 순환 보관본, 중요 작업 직전 최근 50개 보관본, 기존 상파울루 날짜별 하루 보관본을 함께 조회하는 저장 계약과 Supabase 마이그레이션을 작성했다.
- 기간 변경, 자동 계획 적용, 회원 삭제 직전에 서버 최신 문서를 안전 보관하도록 했다. 오프라인이거나 원격 저장이 끝나지 않았거나 보관에 실패하면 파괴적인 작업을 중단한다.
- 보관본 선택 화면을 추가하고 어떤 보관본도 현재 계획에 덮어쓰지 않고 새 ID의 `복구본` 계획으로 열도록 했다.
- 저장소, 저장 조정기, 기간 사본, 복구 사본, 대화상자와 주요 사용자 흐름 테스트를 추가·보강했다.
- 타입 검사, 58개 테스트 파일의 667개 테스트와 전체 커버리지, 프로덕션 빌드, `dist` 스모크 검사를 통과했다. 빌드 화면은 데스크톱과 375px 모바일에서 로그인 진입까지 확인했고 콘솔 오류가 없었다.

## Decisions

- 일반 셀 편집은 최신 작업본 자동 저장으로 유지하고 셀마다 영구 버전을 만들지 않는다. 짧은 실수는 15분 슬롯의 7일 순환 보관으로, 날짜가 지난 복구는 하루 보관으로, 큰 변경 직전 상태는 최근 50개 안전 보관으로 담당한다.
- 기간은 단순 설정값이 아니라 날짜별 셀의 좌표계이므로 수동 계획이 생긴 뒤의 기간 변경은 새 계획 생성으로 취급한다. 명시적으로 입력한 0만 있는 계획도 같은 보호를 받는다.
- 복구는 과거 상태를 현재 행에 덮어쓰는 명령이 아니라 새 계획 사본 생성으로 제한한다. 잘못 복구해도 현재 작업을 다시 잃지 않기 위한 결정이다.
- 중요 작업 보관은 클라이언트가 임의 문서를 업로드하는 방식이 아니라, 인증·workspace 소속·현재 서버 문서 일치를 검사하는 제한된 RPC로 수행한다.
