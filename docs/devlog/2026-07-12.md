### Work Completed

- 회원별 PVP 목표를 시작값 화면에서 `2,400 / 1,500 / 700` 중 직접 선택하도록 변경했으며, 미선택 상태는 검증 오류로 처리했다.
- 선택형 찾기 표지판 `표시 없음 / 1·분홍 / 2·연두 / 3·하늘색`을 추가했다. 회원 카드와 수동 계획표 헤더에 번호와 색상을 표시하되 계산에는 전달하지 않는다.
- PVP 목표 700 회원에게만 같은 총 PV 안에서 약 8일의 커미션 발생을 권장하도록 RuleSet과 계산 엔진을 `2.0.0`으로 갱신했다. 권장 미달은 실패가 아니며 이를 위해 PV를 추가하지 않는 기존 소프트 제약을 유지했다.
- 수동 계획표의 PVP·좌·우 열 머리글 아래에 해당 회원의 시작값을 표시하고, 보름 요약에 직접 선택한 PVP 목표를 표시했다.

### Decisions

- 사용자가 별도 저장·복구 개념을 배울 필요가 없도록 입력할 때 자동 저장하고 앱 시작 시 자동 복원한다.

## 추가 작업 — PVP 300 수당 자격과 하위 조직 공동 기여 반영

### Work Summary

원본 계획표를 다시 설명받는 과정에서 시작 PVP가 300 미만인 회원의 수당 자격과, 아래 회원의 PVP가 본인뿐 아니라 모든 상위 조직에도 함께 기여하는 운영 규칙이 새로 확인되었다. 이 규칙은 자동 계획의 날짜별 가능 여부와 엔진 계산 순서를 바꾸므로 Phase 4 실행 계획의 필수 조건·모델·작업 패키지·시험 항목에 반영했다.

### Work Completed

- 수당 자격 PVP를 `시작 PVP + 해당 날짜까지 직접 추가한 PVP 누계`로 정의하고 커미션 초기화와 별도로 유지하도록 계획했다.
- 당일 추가 PVP를 먼저 누계해 300에 도달하면 같은 날부터 정상 커미션을 허용하도록 명시했다.
- PVP 300 미만에서 발생하는 30% 수당은 자동 계획의 선택지로 인정하지 않고, 그 전에 커미션이 발생하는 후보를 무효로 처리하도록 했다.
- 수동 입력에서 자격 전 커미션이 생긴 경우 회사의 실제 잔액 초기화는 보존하되 정상 커미션으로 세지 않고 쉬운 경고를 표시하도록 엔진 확장 범위를 추가했다.
- `PVP 100 + 좌 300 + 우 300 = 하위 조직 전체 700`이 상위 회원의 연결된 한쪽에 700으로 올라가는 대표 사례를 공동 기여 계산 사례로 기록했다.
- 정확한 1·10단위 숫자는 계속 허용하고, 전체 계산 결과가 같을 때만 100단위 칸을 더 많이 사용하는 계획을 선호하도록 우선순위를 확정했다.
- 새 규칙에 맞춰 Phase 1 계산 규칙 버전을 올린 뒤 자동 최적화가 그 엔진으로 후보를 독립 검증하도록 Phase 4 작업 순서를 수정했다.
- 시작값 33에 당일 267 또는 266을 넣는 경계, 여러 날 누계, 한쪽 실적 이월, 이미 300 이상인 시작값, 자격 전 수동 정산 초기화와 하위 700 전파 시험을 추가했다.

### Decisions

- PVP 300 자격은 비용·커미션 횟수·100단위 편의와 교환할 수 없는 자동 계획의 필수 조건으로 취급한다.
- 자격 전에는 좌·우 값을 무조건 0으로 강제하지 않는다. 한쪽 실적을 쌓는 것은 허용하되 양쪽이 커미션 조건에 도달하지 못하게 한다.
- 30% 수당의 금액을 계산하거나 비교하지 않는다. 다만 수동 입력의 실제 회사 초기화까지 무시하면 이후 잔액이 틀리므로 내부 계산과 경고는 유지한다.
- 하위 회원에게 넣은 직접 PVP는 비용으로 한 번만 세지만 본인의 PVP 목표·자격과 모든 상위 회원의 조직값에 미치는 효과는 전부 계산한다.
- 267 같은 정확한 값이 전체 조직에 더 유리하면 사용한다. 100단위는 강제 입력 단위가 아니라 모든 상위 목표가 같은 경우의 마지막 선호 조건이다.

### Current Status

- Phase 4 실행 계획에 새 자격 규칙과 공동 기여 사례가 구현 계약 수준으로 반영되었다.
- 현재 Phase 1 엔진에는 이 자격 규칙이 아직 구현되지 않았으며, Phase 4 `WP1`에서 규칙 버전과 함께 먼저 확장하도록 계획되어 있다.
- 이번 변경은 문서만 수정했으며 애플리케이션 코드와 현재 수동 계산 동작은 바꾸지 않았다.

### Next Steps

- Phase 4 구현 전 `PRE-WP0`에서 요구사항·기술 설계·계산 사례에 PVP 300 자격 규칙을 동기화한다.
- 새 계산 규칙 버전을 정하고 수동 입력에서 자격 전 정산이 발생했을 때의 결과·경고 계약부터 시험으로 고정한다.
- 자격 조건을 통과한 후보만 최적화에 들어가도록 작은 완전탐색 기준기와 후보 검증기를 구현한다.

## 추가 작업 — PVP 값 100 우선 배치 규칙 확정

### Work Summary

기존의 `100단위 선호`가 100·200·300을 모두 같은 좋은 값으로 취급해, 실제 운영에서 PVP를 거의 항상 100씩 배치하는 습관을 충분히 표현하지 못한다는 점을 확인했다. PVP 값 자체가 100인 칸을 먼저 선호하되 계산상 필요한 정확한 값과 200·300을 막지 않도록 Phase 4 목표 순서를 보완했다.

### Work Completed

- 0이 아닌 PVP 입력칸 중 값이 정확히 100이 아닌 칸 수를 별도 목표값으로 추가했다.
- 모든 중요한 계산 결과가 같다면 `PVP 200 한 번`보다 `PVP 100 두 번`, `PVP 300 한 번`보다 `PVP 100 세 번`을 우선하도록 정의했다.
- PVP 100 선호 뒤에 전체 입력칸의 100단위 배수를 비교하고, 그래도 같으면 가장 큰 단일 PVP 값을 줄이도록 목표 순서를 정했다.
- PVP 67·200·300이 자격 시점, 총 PV, 버려지는 초과 PV나 커미션 결과를 개선하면 언제든 선택할 수 있음을 명시했다.
- PVP 100 분할, 상위 목표를 개선하는 예외값, 최대 PVP 200과 300 비교 시험을 Phase 4 계획에 추가했다.
- 앞서 확인한 Q-SIM-02 초과 PV 계산을 확정 상태로 바꾸고 `PVP 500 / 좌 0 / 우 300`에서 버려지는 값이 200인 사례를 기록했다.

### Decisions

- `PVP 값 100 선호`와 `모든 입력값의 100단위 선호`는 서로 다른 목표로 관리한다.
- PVP 100은 허용값 제한이나 일일 상한이 아니다. 모든 필수 조건과 계산상 이득이 같은 경우에만 적용하는 운영 편의 규칙이다.
- 시작 PVP 33이 자격 300을 넘어 333이 된 경우의 33은 보름 PVP와 자격 누계에 남으므로 정산으로 버려지는 초과 PV에 포함하지 않는다.

### Current Status

- Phase 4 실행 계획의 목표 벡터, 비교 순서, 작업 패키지, 시험, 위험과 완료 조건에 PVP 100 선호가 반영되었다.
- Q-SIM-01부터 Q-SIM-06까지 계획서 안에서는 모두 확정 상태다.
- 애플리케이션 코드는 아직 변경하지 않았다.

### Next Steps

- `PRE-WP0`에서 PVP 100 선호 지표와 Q-SIM-02 확정 공식을 요구사항·기술 설계·계산 사례에 동기화한다.
- 작은 완전탐색 시험으로 PVP 100 선호가 총 PV·초과 손실·커미션 결과를 절대 앞서지 않는지 검증한다.

## 추가 작업 — Phase 4 qualification-aware 자동 계획 구현

### Work Summary

수정된 Phase 4 실행 계획과 연결된 요구사항·기술 설계·계산 사례·Phase 2·3 계획을 원문으로 다시 대조한 뒤, 수당 자격 PVP를 반영한 계산 엔진 3.0.0과 자동 후보 생성·검증·미리보기·현재 탭 체크포인트·수동 계획 적용 흐름을 구현했다. 동시에 브라우저에서 정확한 최적성 증명을 맡길 backend를 검토했으나 Phase 4의 completeness·exact proof 관문을 충족하는 승인 가능한 패키지가 없어, 검증 후보는 제공하되 최적·불가능을 거짓으로 표시하지 않는 경계에서 중지했다.

### Work Completed

- 권위 문서의 Q-SIM-01~06을 최종 동기화했다. 제품 실행은 고정 최대 30분 한 종류로 제한하고 3시간·사용자 지정 실행을 제거했으며, exact PVP 100과 목표 700 총 발생일을 독립 목적 단계에서 제외했다.
- 규칙·계산 엔진을 `3.0.0`으로 올리고 `openingQualificationPvp`를 포함한 다섯 시작값을 도메인·설정·UI 전체에 분리했다.
- 당일 직접 PVP를 먼저 포함하는 비초기화 qualification 누계, 300 경계, 자격 미달 기계적 정산의 실제 reset 보존, full commission 전용 발생일 집계와 위치가 있는 경고를 구현했다.
- `Date` 객체에 의존하지 않는 Gregorian date-only 일요일 판정과 calendar `1.0.0`, 루트 우선·LEFT 후 RIGHT 정본 회원 순서, 마지막 날짜의 authoritative carry를 구현했다.
- 총 신규 PV, full commission 소멸 초과분, 목표 700의 8일 이상 인원과 오름차순 일수 벡터, 일반 non-100 칸, 최대 직접 PVP, 완전한 배정 벡터 순서의 exact comparator를 구현했다.
- 후보 shape·순서·safe integer·negative zero·Sunday·qualification·전체 목표·목적값을 독립 재계산하는 verifier와 bounded tiny oracle, 50명까지 동작하는 결정적 constructive candidate를 추가했다.
- model certificate와 complete proof 없이는 `OPTIMAL/INFEASIBLE`을 만들 수 없고, 미증명 후보는 `RUNNING/TIME_LIMIT/CANCELLED/FAILED` 안에서만 보존되는 상태 계약을 구현했다.
- versioned Web Worker protocol, run ID와 candidate sequence, stale·late message 차단, cooperative cancel 후 terminate fallback, immutable pinned preview와 새 후보 알림을 구현했다.
- session schema를 v2로 올리고 v1에서 자격 PVP를 임의 복사하지 않는 migration을 구현했다. 기존 수동 초안은 보존하되 자격 시작값은 `0`, 시작값 확인은 해제하고 설정 화면으로 되돌린다.
- 최신 검증 후보 하나만 workspace v2에 debounce checkpoint하고 ruleset·engine·objective·calendar·certificate version과 fingerprint가 맞을 때 엔진으로 다시 검증해 복원한다. 계산 결과 전체와 proof frontier는 저장하지 않는다.
- 자동 계획을 수정된 수동 계획에 적용할 때 명시적으로 확인하고, pinned allocation만 기존 문자열 스키마로 원자 변환한 뒤 성공 시 worker를 종료하도록 했다.
- 수동 입력이 자격 300 미만 정산을 만들면 `AUDIT_BLOCKED`로 계산 사용은 막되 실제 reset과 일일·보름 감사 결과는 계속 표시하도록 했다.
- hashed module worker가 실제 `dist`에 있고 앱 번들에서 참조되는지 확인하는 배포 smoke gate를 추가했다.
- 브라우저 exact solver 검토 결과와 중단 조건을 `PHASE_4_SOLVER_FEASIBILITY_SPIKE.md`에 기록했다. 새 solver/WASM 의존성은 추가하지 않았다.

### Decisions

- 과거 로그의 3시간 실행과 exact-PVP-100 독립 선호는 이후 운영자 확정으로 폐기되었다. 이번 구현은 수정된 고정 30분·objective `2.0.0` 계약만 따른다.
- Below-300 정산을 자동 후보에서 금지해도 회사 장부의 실제 초기화를 되돌리지 않는다. 수동 계획은 reset trace를 보존하고 자동 verifier만 후보를 거부한다.
- UI 중위 순회는 표를 가운데 정렬하는 표시 순서로만 사용한다. fingerprint와 최종 타이브레이커는 stable member key와 조직 topology에서 만든 전위 정본 순서를 사용한다.
- Constructive algorithm은 유효한 incumbent를 빨리 제공하지만 완전한 모델 탐색이 아니므로 최적성 또는 불가능을 주장하지 않는다.
- OR-Tools는 지원되는 브라우저 WASM 경로가 없고, 확인한 HiGHS/GLPK wrapper는 tolerance·certificate·50명 worker 관문 증거가 부족했다. 대기만 하는 가짜 30분 탐색 대신 후보를 보존한 `AUTOMATIC_PLAN_PROOF_INCOMPLETE` 실패로 정직하게 종료한다.
- 50명 정규 이진 조직의 constructive 생성과 재검증은 개발 환경에서 26.61ms로 관측됐지만, 이 값은 exact search나 운영 노트북의 성능 보장이 아니므로 시간 임계값 assertion으로 고정하지 않았다.
- GitHub Issue 생성은 외부 쓰기 권한이 명시적으로 승인되지 않아 수행하지 않았다. 따라서 이번 변경은 커밋하지 않았고 issue 연결 commit도 만들지 않았다.
