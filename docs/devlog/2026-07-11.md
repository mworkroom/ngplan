## Decisions

- Phase 1은 자동 최적화나 제품 UI가 아니라 동일 입력에 동일 결과를 내는 순수 계산 코어로 한정했다. 두 장부와 조직 전파의 정확성이 이후 모든 기능의 전제이기 때문이다.
- 일일 장부의 상태와 보름 장부의 원본 누계를 별도 타입과 결과로 유지하고, 일일 초기화가 날짜별 원본을 덮어쓰지 않도록 했다.
- 계획·확정·실제 리비전은 계산 코어가 아니라 후속 애플리케이션 계층의 책임으로 분리했다.
- 최적화용 초과 소멸량 수식은 Phase 1 필수 출력에서 제외하고 Phase 4 결정 사항으로 남겼다.
- 입력 fingerprint는 재현 수단으로 사용하지 않고 Phase 6의 무결성·캐시 기능으로 미뤘다. 재현에는 전체 입력과 당시 RuleSet 본문을 보존하도록 했다.
- 개별 입력뿐 아니라 조직 합계, 이월, 보름 누계와 후속 최적화 점수도 정확한 정수 범위를 검사하도록 설계했다.
- Phase 1 기술 스택은 TypeScript, Vite, Vitest로 확정하고 UI 프레임워크는 Phase 2 전에 결정하기로 했다.
- 보름 작은 쪽에는 보름 PVP 시작값과 신규 PVP 전액을 적용하며 목표 초과분도 자르지 않는다. 일일 PVP 시작잔액은 제외하고 보름 PVP 시작값은 상위 조직에 재전파하지 않는다.
- 날짜별 하위 신규 원본은 발생일에 모든 상위 회원에게 경로당 한 번 연쇄 반영하고 시작·이월 잔액과 정산 결과는 재전파하지 않는다.

### Decisions

- 정규 입력은 모든 반월 날짜와 회원의 완전한 셀 집합으로 받고, `SELF` 방향은 0을 포함한 필드를 요구하며 `CHILD` 방향은 필드가 존재하는 것 자체를 오류로 처리했다. 계산 중 누락값을 임의로 0으로 해석하지 않기 위해서다.
- 계산 전에 입력을 평범한 정규 스냅샷으로 한 번 복사하고 그 동일한 값을 검증과 계산에 사용한다. 접근자나 변경 가능한 객체가 검증 후 다른 값을 제공하는 시점 차이를 막기 위한 결정이다.
- 규칙 버전 `1.0.0`은 버전 문자열뿐 아니라 공식 단계, 목표와 정책 본문 전체가 정본과 일치할 때만 허용한다. 결과가 같은 버전으로 서로 다르게 재현되는 상황을 차단하기 위해서다.
- 회원 키는 임의의 비어 있지 않은 문자열을 지원하므로 회원별 감사 결과는 null-prototype 레코드에 저장했다. `__proto__` 같은 키도 직렬화에서 사라지지 않는다.
- `SKIP_NO_INPUT`은 영업 달력 모드, `SKIPPED`는 정산 실행 상태로 분리했다. 휴무 원인과 실제 정산 여부를 서로 다른 감사 축으로 유지하기 위해서다.
- 자동 최적화, 완성형 UI, 계획·실제 리비전, 저장 기능은 Phase 1 공개 코어에 포함하지 않았다.
