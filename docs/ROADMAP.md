# 피라미드앱 개발 로드맵

> 기준 요구사항: `docs/requirements/pyramid-app-requirements-v2.md`  
> 작성일: 2026-07-14
> 대상 서비스: `https://plan.nangok.app`  
> 배포 저장소: `https://mworkroom.github.io/ngplan`  
> 현재 상태: Phase 4 자동 계획 베타 동결, Phase 6A 핵심 구현·운영 DB·Auth 설정 완료 및 인증된 브라우저 검수·코드 배포 대기

## 1. 로드맵 목적

이 문서는 요구사항 확정부터 최종 운영 배포까지의 전체 개발 순서와 각 Phase의 완료 기준을 정의한다.

가장 큰 제품 위험은 화면 구현이 아니라 다음 계산을 동시에 정확하게 유지하는 데 있다.

- 하위 조직 실적의 상위 연쇄 합산
- 커미션 발생 여부에 따라 초기화 또는 이월되는 일일 장부
- 일일 초기화와 무관하게 원본 실적을 보존하는 보름 장부
- 최소 신규 PV를 찾는 자동 계획과 실제값 이후의 부분 재시뮬레이션

따라서 Phase 1에서 결정론적 계산 코어를 먼저 완성하고, 이후 모든 화면과 자동화 기능이 같은 코어를 사용하도록 한다.

## 2. 진행 원칙

1. 요구사항에서 확정되지 않은 규칙은 임의로 제품 규칙으로 만들지 않는다.
2. 계산 코어는 UI, 저장소, 네트워크에 의존하지 않는 순수 로직으로 유지한다.
3. 날짜별 원본 입력과 계산된 파생값을 분리하며 원본을 계산 결과로 덮어쓰지 않는다.
4. 모든 계산 결과는 어떤 입력과 규칙 버전에서 나왔는지 추적할 수 있어야 한다.
5. 자동 계획이 만든 결과도 독립된 계산 코어로 다시 검증한다.
6. 과거 확정 기록은 당시 데이터와 규칙 버전을 보존하며 현재 규칙으로 조용히 바꾸지 않는다.
7. 각 Phase는 이전 Phase의 자동 테스트와 완료 기준을 깨뜨리지 않은 상태에서 종료한다.
8. 화면의 누적 PVP 시작값은 수당 자격과 개인 PVP 목표 부족분에 사용하고 첫날 일일 PVP 잔액과 보름 좌·우 적용량에서는 제외한다. 세 내부 장부의 의미와 변화는 계속 분리한다.
9. 자동 계획의 비즈니스 순서는 화면 표시 순서와 분리하며, 안정적인 회원 키와 조직 구조에서 파생한 순서만 사용한다.

## 4. Phase 1 — 결정론적 계산 코어

### 4.1 목표

주어진 조직, 시작값, 날짜별 직접 배정값을 받아 항상 같은 일일·보름 결과를 반환하는 계산 엔진을 만든다. 자동으로 실적을 배정하는 기능은 포함하지 않는다.

### 4.2 구현 전 진입 조건

완료된 조건:

- `TECHNICAL_DESIGN.md`의 **Q-CALC-01~Q-CALC-06** 결정이 반영되었다.
- 계산용 레벨 개념은 제거했다. 회원별 PVP 목표는 2,400·1,500·700 중 직접 선택한다.
- 이름 앞 번호와 색상은 계산과 무관한 선택형 찾기 표지판이다.
- 프로젝트는 루트 한 명의 연결된 트리이며 일요일은 `SKIP_NO_INPUT`으로 확정되었다.
- Phase 1 기술 스택은 TypeScript, Vite, Vitest로 승인되었다. UI 프레임워크는 Phase 2 전에 결정한다.
- `CALCULATION_CASES.md`의 Phase 1 계산 규칙 차단 사례가 모두 확정되었다.
- 현재 회원별 좌·우 목표와 Phase 4 환산 계약을 포함한 규칙·엔진은 `8.0.0`이다.

완료된 작업 관리 조건:

- 구현 작업을 GitHub Issue #1에 연결했다.

### 4.3 상세 범위

1. 상반기 1~15일과 하반기 16일~월말 날짜를 생성하고 일요일을 식별한다.
2. 회원, 상위 회원, 좌·우 배치, `스스로` 방향, PVP 목표, 찾기 표지판, 평생 누적 PVP 달성 현황과 일일 좌·우 시작 잔액을 표현한다. 내부 일일 PVP 시작 잔액은 0으로 둔다.
3. 중복 회원 ID, 중복 슬롯, 고아 회원, 순환, 연결되지 않은 조직, 연결 방향 직접 입력을 검증한다.
4. 하루의 직접 입력을 하위부터 합산하여 각 회원의 신규 PVP·조직 좌·조직 우 원본값을 계산한다.
5. 회원별 전일 잔액과 당일 원본값으로 정산 전 잔액을 만든다.
6. PVP를 판정용 작은 쪽에 전량 적용하고 공식 단계 중 가장 높은 일일 커미션 단계를 판정한다.
7. 커미션 발생 시 PVP·좌·우와 초과분을 모두 0으로 만들고, 미발생 시 원래 세 잔액을 그대로 이월한다.
8. 일일 초기화와 별도로 날짜별 원본값을 누적하여 개인 PVP 목표와 보름 좌·우 목표를 판정한다.
9. 전체 반월을 날짜순으로 계산하고, 각 중간값을 감사 가능한 결과로 반환한다.
10. 확정된 계산 사례를 단위·통합 테스트로 자동 검증한다.

### 4.5 작업 순서

1. 완료된 최초 계산 계약과 당시 규칙 버전 `2.0.0`을 구현 Issue에 연결한다. 후속 규칙 개정은 각 Phase 계약과 개발 로그에서 추적한다.
2. 프로젝트 도구와 엄격한 타입 검사를 구성한다.
3. 도메인 타입, 상수, 입력 검증을 만든다.
4. 조직 전파 계산을 구현하고 독립 테스트를 통과시킨다.
5. 일일 장부를 구현하고 공식 단계 전체와 경계를 검증한다.
6. 보름 장부를 구현하고 일일 장부와 독립적으로 원본이 보존되는지 검증한다.
7. 기간 계산기를 조합하고 다일·다단계 조직 통합 사례를 검증한다.
8. 전체 타입 검사, 테스트, 커버리지 검사, 빌드를 실행하고 개발 로그를 작성한다.

### 4.6 완료 기준

- `CALCULATION_CASES.md`에서 Phase 1 대상으로 표시된 모든 확정 사례가 자동 테스트로 통과한다.
- 300, 700, 1,500, 2,400, 6,000, 20,000, 60,000의 직전·정확한 경계를 검증한다.
- 커미션 발생 시 초과분까지 모두 소멸하고 미발생 시 PVP·좌·우가 원래 항목으로 이월된다.
- 일일 잔액 초기화가 보름 원본 누적값을 지우지 않는다.
- 하위 실적은 모든 상위 회원에게 날짜당 한 번만 반영된다.
- 연결 방향은 파생값이며 PVP와 `스스로` 방향만 직접 입력할 수 있다.
- 계산 함수가 입력 데이터를 변경하지 않고 같은 입력·규칙 버전에 같은 결과를 반환한다.
- 잘못된 값과 조직은 부분 결과를 만들기 전에 식별 가능한 오류로 거부된다.
- 타입 검사, 전체 테스트, 도메인·계산 규칙 분기 커버리지 95%, 프로덕션 빌드가 통과한다.
- 실제 변경과 결정 과정이 오늘자 한국어 개발 로그에 기록된다.

### 4.7 제외 범위

- 자동 신규 PV 배정과 최적화
- 완성형 조직 편집 화면과 가로형 작업표
- 계획 확정, 실제값 입력, 차이 비교, 부분 재시뮬레이션
- 영구 저장, 계정, 기기 간 동기화, 종료 기록
- PDF·스프레드시트 등 전달용 출력
- 운영 배포

## 5. Phase 2 — 프로젝트와 조직 입력

### 목표

반월 프로젝트를 만들고 피라미드 그림을 보며 회원, 좌·우 연결, `스스로` 방향, PVP 목표, 찾기 표지판과 시작값을 역할별로 입력할 수 있게 한다.

### 주요 결과

- 상·하반기 `IN_PROGRESS` 프로젝트 생성, 기간 기반 기본 제목과 수동 제목 보존
- 불완전한 문자열과 임시 미배치 상태를 허용하는 인메모리 `ProjectSetupDraft`
- 회원 ID·이름·PVP 목표·찾기 표지판과 부모 기준 좌·우 배치의 카드형 편집
- 각 카드의 명시적 왼쪽·오른쪽 `+` 슬롯과 파생 `SELF/CHILD` 표시
- 이번 기간 PVP 목표, 0~2,400 누적 PVP 시작값과 일일 좌·우 시작 잔액의 네 항목 입력, 0 기본값과 회사 시스템 확인 상태. 내부 일일 PVP 시작 잔액은 0으로 고정
- 중간 회원 제외 시 후손 서브트리를 삭제하지 않는 재배치 대기열과 한 자식 명시적 승격
- Phase 1의 기간·조직 검증을 재사용한 오류·경고 피드백과 불변 `ProjectSetupBundle`
- 어떤 초안 변경도 활성 설정 묶음을 즉시 해제하는 `EDITING/READY` 전이
- 이전 프로젝트 값의 자동 이월 방지와 현재 브라우저 `localStorage` 작업 스냅샷 안내. 화면 이동·새로고침·브라우저 재실행은 보호하지만 사이트 데이터 삭제 시 사라지며 프로젝트 목록이나 기기 간 동기화는 아니다.
- React 카드 UI, 키보드 조작, 오류 위치 이동, 반응형 배치와 넓은 트리 가로 스크롤

### 종료 기준

유효한 단일 루트·연결·비순환 조직과 확인된 시작값으로 Phase 3가 소비할 설정 묶음을 만들 수 있다. 잘못된 연결, 미배치 서브트리, 중복 회원 ID, 미확인 시작값은 게시 전에 차단되고, 경고는 보존된다. 회원 제외와 재연결은 살아 있는 후손 데이터를 다시 입력하지 않고 수행할 수 있다.

### Phase 경계

- Phase 2는 날짜별 배정 셀, 계획표와 계산 결과를 만들지 않는다.
- 계획 리비전이 생기기 전의 인메모리 설정만 자유롭게 편집한다.
- 계획 이후 조직 변경은 안정적인 회원 키와 비파괴적 서브트리 명령을 이용해 Phase 5에서 새 조직 스냅샷과 재계산으로 처리한다.
- 현재 브라우저 작업의 클라우드 저장·복구·하루 보관본·숨김/복원은 Phase 6A에서 처리한다. `CLOSED`·종료 잠금·읽기 전용 기록은 전체 Phase 6의 후속 범위다.

## 7. Phase 4 — 자동 계획 최적화

### 목표

조직과 시작값을 기준으로 목표를 충족하는 최소 신규 PV 계획을 자동 생성한다.

### 주요 결과

- 최대 57명 조직에서 브라우저 작업 스레드로 실행하는 고정 30분 단일 자동 계획. 3시간·사용자 지정·숨은 연장 모드는 제공하지 않는다.
- 개인 PVP 및 보름 좌·우 목표와 일요일 신규 배정 금지를 하드 제약으로 다루는 계획 생성
- 화면의 누적 PVP 시작값은 평생 달성 현황이며 상한은 2,400이다. 수당 자격과 개인 PVP 목표 부족분의 시작점으로 사용하고 첫날 일일 PVP 잔액과 보름 좌·우 적용량에서는 제외한다. 좌·우 시작 잔액은 사용자가 입력한다.
- 누적 PVP 2,400 회원에게는 신규 PVP를 배정하지 않고, 나머지 회원의 기간 신규 PVP 합계도 `2,400 - 누적 PVP 시작값` 이하로 제한한다.
- 수당 자격 PVP는 `누적 PVP 시작값 + 해당 날짜까지의 직접 신규 PVP 누계`로 계산하고, 당일 신규 PVP를 포함한 값이 300 이상일 때만 그날 정상 커미션을 허용한다.
- PVP 300 미만의 기계적 정산은 실제 초기화 결과를 계산 엔진에 보존한다. 자동 후보에서는 금지하고, 수동 계획에서는 계산을 막는 안내로 표시한다.
- 일일 PVP는 현재 일일 장부 값을, 보름 PVP는 이번 기간 신규 PVP 합계만 좌·우 중 작은 쪽에 전량 적용한다.
- 각 회원은 보름 판정 좌·우 목표를 2,500 또는 1,500으로 선택하며 새 기간은 2,500으로 시작한다. 목표 행은 누적 PVP를 뺀 신규 PVP 부족분과 회원별 좌·우 목표를 하위부터 순수 재귀 합산한다. 수동 계획·계산 엔진·자동 계획은 두 값과 혼합 조직을 같은 회원별 목표로 지원한다.
- 자동 계획의 직접 PVP와 `스스로` 좌·우는 0 또는 30 이상으로 제한한다. 수동 계획과 실제 결과는 계속 1 PV 단위를 허용하고, 100의 배수는 소프트 선호로만 사용한다.
- 첫 8일에 배정을 끝내지 않고 반월 전체 영업일을 계획 범위로 사용한다. 모든 회원·영업일의 직접 실적을 강제하지는 않는다.
- 실제 입력 가능 영업일 수 `N`과 최소 목표 총량으로 맨 위 회원의 총량상 정상 커미션 목표 `U`를 동적으로 계산한다. 시작 좌·우 잔액은 첫 full commission과 reset 한 번에만 사용하고 남은 기간은 opening 없는 총량식으로 계산한다. `U=N`이면 최소 총 신규 PV 계획 안에서 모든 영업일 커미션이 운영 목표이고, 극소 조직은 이론상 최대 `U<N`을 목표로 한다.
- 상위 회원에게 함께 기여하는 배치를 활용하되 직접 신규 PV는 입력 위치에서 한 번만 비용으로 센다.
- 정상 커미션 발생일과 운영자가 말하는 수당 횟수를 분리한다. 수당 환산은 300=1회, 700=2회, 1,500=4회, 2,400=8회이며, 예를 들어 700단계 4일은 발생일 4일·환산 8회다.
- 목적 순서는 `총 신규 PV 최소화 → 같은 최소 비용에서 맨 위 회원 U 발생일 목표 미달 최소화 → 확인된 수당 금액 최대화 → 일일 소멸 초과분 최소화 → 목표 1,500·2,400 회원의 구조 보정 환산 미달 벡터 최소화 → 목표 700 회원의 구조 보정 환산 미달 벡터 최소화 → 비용이 같은 미래 누적 PVP 투자 최대화 → 0이 아닌 직접 입력 중 100의 배수가 아닌 칸 최소화 → 최대 직접 PVP 칸 최소화 → 정본 순서 타이브레이커`다. 맨 위 회원은 일반 공평성 벡터에서 제외하고 별도 발생일 shortfall로 비교한다. 조직 깊이와 화면 마커는 수당 우선순위를 정하지 않는다.
- Constructive가 `U`를 채우지 못해도 나머지 계산 계약을 통과한 후보는 `맨 위 회원 전체 영업일 목표 미달 X일` 안내와 함께 verified fallback으로 제공한다. 총 신규 PV가 같은 목표 달성 후보가 우선하지만 추가 구매로 일수를 늘리지는 않으며, exact 완전 증명 없이 `INFEASIBLE`로 표시하지 않는다.
- Automatic-plan policy는 `8.0.0`, objective는 `7.0.0`, Ruleset·engine은 `8.0.0`, request/fingerprint/checkpoint/model schema와 worker protocol은 `4.0.0`이다. Policy 8.0은 회원별 1,500/2,500 혼합 목표를 지원하고 이전 자동 후보를 무효화한다.
- 확인된 수당은 300=60,000원=환산 1회, 700=120,000원=2회, 1,500=240,000원=4회, 2,400=480,000원=8회다. 6,000 이상 단계의 금액·환산은 추측하지 않고, 해당 단계가 후보 비교에 나타나면 수당표가 추가될 때까지 자동 순위를 안전하게 중단한다.
- 같은 8회 이론상 상한에서 목표 700의 실제 환산 `[7,7,7]`은 미달 `[1,1,1]`이므로 실제 `[0,8,8]`의 미달 `[8,0,0]`보다 우선한다. 환산 8회 이상 인원과 총 환산 횟수는 화면 표시용 통계일 뿐 별도 목적함수 단계가 아니다.
- PVP 값이 정확히 100인 칸을 독립적으로 선호하지 않는다. 100단위 가독성은 더 높은 모든 목적이 같은 경우에만 적용한다.
- 자동 계획의 정본 회원 순서는 맨 위 회원부터 시작해 각 회원의 왼쪽 가지를 오른쪽 가지보다 먼저 방문한다. 수동 작업표의 가운데 정렬용 중위 순회 화면 순서와 혼동하지 않는다.
- 기간 마지막의 이월 잔액은 계산 엔진 결과대로 보존하며, 명시적인 소멸 규칙이 없는 한 끝 잔액 벌점이나 낭비로 계산하지 않는다.
- 최적 증명 완료와 제한 시간 안에 찾은 검증 계획을 구분하고, 후보 전체를 Phase 1 계산 코어로 독립 검증한다.
- 현재 브라우저 작업 스냅샷에는 최신 검증 후보와 최소 호환 정보만 체크포인트한다. 전체 탐색 상태나 증명 진행을 저장·복원했다고 표시하지 않는다.

### 종료 기준

1·10·20·57명 대표 조직에서 목표 충족과 정확한 목적 순서를 재현하고, 생성·복원·적용되는 모든 후보를 버전이 맞는 Phase 1 계산 코어로 독립 검증할 수 있다. 고정 30분 안에 증명이 끝나지 않으면 검증된 최선 후보만 `최적 미증명` 상태로 제공하며, 검증 후보가 없으면 그 사실을 설명한다.

## 9. Phase 6 — 저장, 종료 기록, 복구와 내보내기

### 목표

진행 중 작업과 종료 기록을 안전하게 보존하고, 필요한 과거 자료를 다시 읽을 수 있게 한다.

### 9.1 Phase 6A — 클라우드 안전 저장

Phase 4 자동 계획은 베타 동결하고, [Phase 6A 실행 계획](plans/PHASE_6A_EXECUTION_PLAN_ko.md)에 따라 저장 기능을 먼저 구현했다. 운영 DB schema·RLS와 애플리케이션의 클라우드/IndexedDB 저장 경로를 적용했고, 공유 Supabase Auth의 프로젝트 전역 신규 가입을 차단하고 ngplan 운영 Redirect URL을 추가했다. 인증된 실제 브라우저 운영 검수와 코드 배포가 남아 있다.

- 기존 Supabase 프로젝트와 기존 로그인 방식을 재사용한다.
- 계획 업무 시간대는 `America/Sao_Paulo`로 고정한다. 기기 위치와 서버 리전은 계획 날짜를 바꾸지 않는다.
- 최신 계획 전체를 Supabase 원본에 자동 저장하고 IndexedDB를 오프라인 사본으로 사용한다.
- 충돌 선택 화면 없이 마지막 도착 작업본으로 자동 덮어쓴다.
- 계획별 상파울루 날짜 하루 보관본을 한 개 유지한다.
- 계획 목록의 숨김/복원만 제공하며 `CLOSED` 잠금은 만들지 않는다.
- 기존 `localStorage` 이전, 특별 스냅샷, 셀별 영구 이력, 외부 백업은 제외한다.
- Supabase Free 플랜의 제한을 전제로 하며 플랫폼 자동 백업이나 PITR을 전제로 하지 않는다.

#### Phase 6A 종료 기준

엄마가 저장 충돌이나 복구 방식을 선택하지 않아도 로그인 후 계획을 편집할 수 있고, 오프라인 입력이 로컬에 남으며, 재연결 후 원격에 자동 반영된다. 상파울루 날짜별 하루 보관본과 숨김/복원이 동작하고, 두 허용 계정 외에는 자료가 노출되지 않는다.

### 9.2 전체 Phase 6 후속 범위

#### 주요 결과

- 저장 방식 결정에 맞춘 자동 저장과 복구
- 데이터 스키마, 계산 규칙 버전과 당시 RuleSet 본문 보존
- 종료 당시 조직·시작값·확정 계획·실제값·계산 결과 스냅샷
- 종료 프로젝트 잠금과 새 프로젝트 자동 이월 금지
- 합의된 전달·백업 형식의 내보내기와 가져오기
- 손상·버전 불일치 데이터에 대한 안전한 오류 처리

#### 종료 기준

앱 재실행 뒤 진행 작업을 복구할 수 있고, 종료 기록은 계산 규칙이 바뀌어도 당시 결과를 유지하며, 백업본으로 복원할 수 있다.

---

## 10. Phase 7 — 릴리스 후보 품질 검증

### 목표

실제 업무 규모에서 정확성, 성능, 사용성, 접근성, 데이터 안전성을 검증하고 운영 절차를 준비한다.

### 주요 결과

- 전체 계산·최적화 정답 사례 회귀 검증
- 실제 규모 조직과 반월 데이터의 성능 측정
- 대형 가로표 탐색과 핵심 흐름 사용성 검증
- 키보드 사용, 명도, 오류 안내 등 접근성 점검
- 지원 브라우저와 최소 화면 크기 확정
- 저장 실패, 데이터 손상, 배포 실패, 롤백 훈련
- 개인정보 취급과 백업·복구 절차 점검

### 종료 기준

치명적 결함이 없고, 합의된 지원 환경에서 핵심 업무 흐름과 전체 회귀 테스트가 통과하며, 복구와 롤백 절차가 검증된다.

---

## 11. Phase 8 — 프로덕션 배포

### 목표

검증된 릴리스 후보를 GitHub Pages와 사용자 도메인에 배포하고 지속 가능한 릴리스 절차를 확립한다.

### 주요 결과

- 검증을 통과한 버전만 배포하는 자동 릴리스
- GitHub Pages 주소와 `plan.nangok.app` 연결
- HTTPS, 직접 경로 접근, 새로고침, 캐시 갱신, 오류 페이지 확인
- 배포 버전과 소스 변경 이력의 추적
- 배포 후 핵심 흐름 스모크 테스트
- 이전 정상 버전으로 되돌리는 절차

### 최종 완료 기준

- 운영 주소에서 프로젝트 생성부터 조직 입력, 계획, 실제 반영, 종료 기록 열람까지 핵심 흐름이 정상 작동한다.
- 배포 버전과 계산 규칙 버전을 추적할 수 있다.
- 오류 발생 시 데이터 손실 없이 이전 정상 버전으로 복구할 수 있다.
- 운영 및 사용자 안내 문서가 최신 상태다.
