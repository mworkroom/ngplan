# 피라미드앱 계산 정답 사례

> 기준 요구사항: `docs/requirements/pyramid-app-requirements-v2.md`  
> 작성일: 2026-07-11  
> Phase 4 계약 개정일: 2026-07-19
> 목적: 계산 엔진, 자동 계획기, 부분 재시뮬레이션의 입력과 기대 결과를 사람이 검토 가능한 형태로 고정

## 1. 사용 방법

각 사례의 ID는 향후 자동 테스트 이름과 오류 메시지에 그대로 사용한다.

| 상태 | 의미 |
|---|---|
| **확정** | 요구사항만으로 입력과 기대 결과가 하나로 정해짐 |
| **설계 계약** | 안전한 데이터 구조를 위해 기술 설계에서 정한 검증 동작 |
| **정답 보류** | 요구사항에 둘 이상의 해석이 있어 질문 답변 전에는 테스트 정답으로 고정하지 않음 |

`정답 보류` 사례는 구현하지 않는다. `TECHNICAL_DESIGN.md`의 해당 질문에 답을 반영한 뒤 `확정`으로 바꾸고 기대 결과 하나만 남긴다.

## 2. 공통 표기

- 별도 언급이 없으면 모든 시작값과 입력값은 0이다.
- `P`, `L`, `R`은 각각 PVP, 좌, 우 PV다.
- `SELF L/R`은 자식이 없는 방향에 직접 배정한 원본값이다.
- `T`는 한 회원의 해당 날짜 서브트리 총 실적 `P + L + R`이다.
- `carryIn`과 `carryOut`은 일일 장부의 `P/L/R` 잔액이다.
- `assessed L/R`은 PVP를 작은 쪽에 가상 적용한 판정값이다.
- `tier = 없음`은 양쪽이 최저 단계 300을 함께 통과하지 못했다는 뜻이다.
- 일일 PVP 적용은 원본 `P/L/R`을 변경하지 않는다.
- 보름 원본 합계에는 날짜별 조직 원본만 들어가며 일일 초기화로 지워지지 않는다.
- `총 신규 PV`는 PVP와 `SELF L/R` 직접 입력을 한 번씩만 합한 값이다. 상위 전파값은 다시 더하지 않는다.
- 날짜가 `D1`, `D2`로 표시된 사례는 서로 다른 영업일을 뜻한다.

### Phase 4 버전 계약

- 누적 PVP 원천 분리, 회원별 좌·우 목표, 순수 재귀 목표와 수당 환산을 포함한 현재 규칙 계산 계약과 엔진 계약은 `8.0.0`이다.
- 자동 계획 request/fingerprint/checkpoint/model/certificate와 worker protocol은 `4.0.0`, 정책과 목적함수는 `7.0.0`, calendar는 `1.0.0`이다. 이전 환산 횟수·깊이 기반 후보, 체크포인트와 모델 인증서는 호환되지 않는다.
- 수동 계획과 계산 엔진은 회원별 좌·우 각 2,500 또는 1,500을 지원한다. 현재 자동 계획은 모든 활성 회원이 2,500인 경우만 지원하며 1,500 회원이 있으면 요청 전에 차단한다.
- 제품의 `PVP 시작값`은 0~2,400 회사 누적 달성값이다. 정규화 시 같은 값을 `openingQualificationPvp`와 `fortnightPvpOpeningCredit`에 기록하고 `dailyCarryPvp`는 0으로 기록한다. 일일 좌·우 시작값은 별도 사용자 입력이다.
- `qualificationPvp`는 `openingQualificationPvp + 해당 날짜까지의 직접 신규 PVP 누계`이며 일일 정산으로 초기화되지 않는다. 당일 직접 PVP를 먼저 포함한 뒤 300 자격을 판정한다.
- 자동 계획은 회사 누적 PVP와 이번 기간 신규 PVP 합이 2,400을 넘는 값을 배정하지 않는다. 수동 계획과 실제값은 불가피한 초과 PVP를 입력할 수 있으며, 손해 가능성을 안내하고 입력값 그대로 일일·보름·조직 계산을 계속한다.
- Phase 1 수동·실제값은 정확한 1 PV 정수를 허용하지만 Phase 4 자동 후보의 직접값은 0 또는 30 이상이다. 39는 허용되고 1~29는 금지된다.
- `FULL_COMMISSION`은 qualification PVP 300 이상에서 발생한 공식 단계다. 300 미만에서 회사 정산이 기계적으로 발생한 경우 실제 초기화 결과는 보존하되 `BELOW_QUALIFICATION_SETTLEMENT`로 구분하고 자동 계획에서 금지하며 full commission 일수에 포함하지 않는다.
- Phase 4의 날짜는 유효한 ISO `YYYY-MM-DD` 영업일 값이다. 요일과 일요일 판정은 호스트 시간대나 로캘에 의존하지 않는다.

## 3. 조직 구조와 원본 전파

### ORG-001 — 한 단계 왼쪽 전파

**상태:** 확정 · **대상:** Phase 1

조직:

- A는 루트다.
- A의 왼쪽 자식은 B, 오른쪽은 `SELF`다.
- B의 양쪽은 `SELF`다.

하루 입력:

| 회원 | P | SELF L | SELF R |
|---|---:|---:|---:|
| A | 0 | 입력 불가 | 50 |
| B | 100 | 200 | 300 |

기대 결과:

| 회원 | 원본 P | 원본 L | 원본 R | T |
|---|---:|---:|---:|---:|
| B | 100 | 200 | 300 | 600 |
| A | 0 | 600 | 50 | 650 |

A의 왼쪽에는 B의 `P + L + R = 600`이 한 번 반영된다.

### ORG-002 — 다단계 연쇄 전파

**상태:** 확정 · **대상:** Phase 1

조직은 `A 왼쪽 ← B 왼쪽 ← C`의 사슬이며, 표에 적지 않은 방향은 `SELF`다.

하루 입력:

| 회원 | P | SELF L | SELF R |
|---|---:|---:|---:|
| A | 25 | 입력 불가 | 50 |
| B | 50 | 입력 불가 | 100 |
| C | 100 | 200 | 300 |

기대 계산:

1. `T(C) = 100 + 200 + 300 = 600`
2. `L(B) = 600`, 따라서 `T(B) = 50 + 600 + 100 = 750`
3. `L(A) = 750`, 따라서 `T(A) = 25 + 750 + 50 = 825`

### ORG-003 — 연결 방향 직접 입력 거부

**상태:** 설계 계약 · **대상:** Phase 1

- A의 왼쪽에 B가 연결되어 있다.
- 같은 날짜에 A의 `SELF L = 1`을 원본으로 전달한다.

**기대 결과:** 계산을 시작하지 않고 `CONNECTED_SIDE_ALLOCATION` 오류를 A·날짜·왼쪽 위치와 함께 반환한다.

### ORG-004 — 조직 순환 거부

**상태:** 설계 계약 · **대상:** Phase 1

- A의 부모를 B로 둔다.
- B의 부모를 A로 둔다.

**기대 결과:** `ORGANIZATION_CYCLE` 오류를 반환하고 계산 결과를 만들지 않는다.

### ORG-005 — 같은 슬롯의 두 자식 거부

**상태:** 설계 계약 · **대상:** Phase 1

- B와 C를 모두 A의 왼쪽 자식으로 둔다.

**기대 결과:** `PARENT_SIDE_OCCUPIED` 오류를 반환한다.

### ORG-006 — 하위 실적은 상위의 PVP가 아님

**상태:** 확정 · **대상:** Phase 1

- 회원 A의 왼쪽 자식은 B다.
- B에 PVP 700을 배정하고 다른 값은 모두 0이다.

**기대 결과:**

- B의 PVP 원본은 700이고 `T(B) = 700`이다.
- A의 원본 왼쪽은 700이다.
- A 자신의 신규 PVP는 0이다.
- A의 개인 PVP 판정량은 이 입력만으로 늘지 않으며, 시작 PVP도 0이면 목표 700이 그대로 남는다.

## 4. 일일 커미션 장부

### DAY-001 — PVP로 작은 쪽을 채워 300 달성

**상태:** 확정 · **대상:** Phase 1

입력:

- `carryIn = P 0 / L 0 / R 0`
- 오늘 원본 `P 100 / L 200 / R 300`

기대 결과:

| 항목 | 값 |
|---|---|
| 정산 전 | `P 100 / L 200 / R 300` |
| PVP 적용 방향 | 왼쪽 |
| 판정값 | `L 300 / R 300` |
| 커미션 | 300 단계, 1회 |
| 정산 후 | `P 0 / L 0 / R 0` |
| 보름 원본 | `P 100 / L 200 / R 300`을 그대로 보존 |

### DAY-002 — 300 미달 시 세 잔액 그대로 이월

**상태:** 확정 · **대상:** Phase 1

입력은 `P 100 / L 200 / R 100`이다.

기대 결과:

- 작은 쪽 오른쪽에 PVP 100을 적용한 판정값은 `L 200 / R 200`이다.
- 커미션 단계는 없다.
- `carryOut = P 100 / L 200 / R 100`이다.
- PVP를 오른쪽 잔액에 합쳐 `P 0 / L 200 / R 200`으로 저장하면 오답이다.

### DAY-003 — 전일 이월과 다음 날 원본의 합으로 커미션 발생

**상태:** 확정 · **대상:** Phase 1

| 날짜 | carryIn | 오늘 원본 | 판정 | 결과 |
|---|---|---|---|---|
| D1 | `0/0/0` | `P100/L200/R100` | `L200/R200` | 미발생, `carryOut=100/200/100` |
| D2 | `100/200/100` | `P0/L0/R200` | PVP가 왼쪽에 적용되어 `L300/R300` | 300 단계, `carryOut=0/0/0` |

### DAY-004 — 공식 단계 전체의 경계

**상태:** 확정 · **대상:** Phase 1

모든 행은 `P = 0`, `L = R = 판정 최솟값`인 독립 사례다.

| 판정 최솟값 | 기대 단계 |
|---:|---:|
| 299 | 없음 |
| 300 | 300 |
| 699 | 300 |
| 700 | 700 |
| 1,499 | 700 |
| 1,500 | 1,500 |
| 2,399 | 1,500 |
| 2,400 | 2,400 |
| 5,999 | 2,400 |
| 6,000 | 6,000 |
| 19,999 | 6,000 |
| 20,000 | 20,000 |
| 59,999 | 20,000 |
| 60,000 | 60,000 |
| 80,000 | 60,000 |

299를 제외한 모든 행은 커미션 1회가 발생하고 정산 후 세 잔액이 0이다.

### DAY-005 — 하루에는 가장 높은 단계 한 번만 발생

**상태:** 확정 · **대상:** Phase 1

- 입력: `P 0 / L 1,600 / R 1,500`
- 기대 단계: 1,500
- 발생 횟수: 1회
- 300, 700, 1,500을 각각 한 회로 세어 3회로 기록하면 오답이다.

### DAY-006 — 큰 초과분까지 전량 초기화

**상태:** 확정 · **대상:** Phase 1

- 입력: `P 0 / L 10,000 / R 300`
- 기대 단계: 300
- 기대 `carryOut`: `0/0/0`
- 왼쪽 9,700을 이월하면 오답이다.

### DAY-007 — PVP 적용 후 작은 쪽이 역전되어도 재분배하지 않음

**상태:** 확정 · **대상:** Phase 1

- 입력: `P 500 / L 0 / R 300`
- PVP를 왼쪽에 전량 적용한 판정값: `L 500 / R 300`
- 기대 단계: 300
- 기대 `carryOut`: `0/0/0`
- PVP를 300과 200으로 나누거나 오른쪽으로 다시 옮기면 오답이다.

### DAY-008 — 미발생 PVP는 PVP 항목으로 보존

**상태:** 확정 · **대상:** Phase 1

- 입력: `P 250 / L 0 / R 100`
- 판정값: `L 250 / R 100`
- 기대 단계: 없음
- 기대 `carryOut`: `P 250 / L 0 / R 100`

### DAY-009 — 이월 PVP는 다음 날의 작은 쪽에 다시 적용

**상태:** 확정 · **대상:** Phase 1

| 날짜 | 정산 전 | PVP 적용 | 결과 |
|---|---|---|---|
| D1 | `P100/L100/R250` | 왼쪽 → `L200/R250` | 미발생, 세 값 이월 |
| D2 | 전일 이월 + `P0/L200/R0` = `P100/L300/R250` | 오른쪽 → `L300/R350` | 300 단계, 전량 0 |

PVP 적용 방향은 PVP가 처음 생긴 날에 고정되지 않는다.

### DAY-010 — 일일 초기화 후에도 보름 원본은 남음

**상태:** 확정 · **대상:** Phase 1

| 날짜 | 원본 P | 원본 L | 원본 R | 일일 결과 |
|---|---:|---:|---:|---|
| D1 | 100 | 200 | 300 | 300 단계 후 일일 잔액 0 |
| D2 | 100 | 100 | 0 | 미발생 |

기대 보름 원본 누계는 `P 200 / L 300 / R 300`이다. D1을 0으로 덮어써 `P 100 / L 100 / R 0`으로 계산하면 오답이다.

### DAY-P01 — 자식 이월 잔액의 상위 재전파 금지

**상태:** 확정 · **대상:** Phase 1

조직은 A의 왼쪽 자식 B다.

- D1 B 원본: `P100/L200/R100`, 따라서 `T(B,D1)=400`; B는 커미션 미발생으로 그대로 이월한다.
- D2 B 신규 원본: 모두 0.

**기대 결과:**

- A의 D1 원본 왼쪽은 400이다.
- A의 D2 **원본** 왼쪽은 0이다.
- B의 D1 `carryOut`은 `P100/L200/R100`이지만 A에게 재전파하지 않는다.
- A가 D1에 커미션을 받지 않았다면 A 자신의 D2 `carryInLeft`에 D1의 400이 남고, D2 원본 왼쪽 0을 더한 정산 전 왼쪽도 400이다.

### DAY-P02 — 자식의 당일 초기화와 부모 원본의 독립

**상태:** 확정 · **대상:** Phase 1

- A의 왼쪽 자식 B에 하루 `P100/L200/R300`이 발생한다.
- B는 PVP 적용 후 300 단계 커미션을 받고 일일 잔액이 0이 된다.

**기대 결과:** B의 판정값은 `L300/R300`, 단계는 300, `carryOut=0/0/0`이다. B의 정산 결과와 무관하게 `T(B)=100+200+300=600`이고, A의 그날 원본 왼쪽은 600이다.

### DAY-P03 — 좌·우 동률의 PVP 적용 표시

**상태:** 확정 · **대상:** Phase 1

- 입력: `P100/L300/R300`
- 동률 정책에 따라 `pvpAppliedSide=LEFT`다.
- 판정값은 `L400/R300`이다.
- 커미션 단계는 300, 발생 횟수는 1회, `carryOut=0/0/0`이다.
- 화면에는 `동률 → 좌 적용`으로 표시한다.

## 5. 보름 PVP와 좌·우 목표

### HALF-001 — 목표 1,500의 시작 PVP가 신규 필요량을 줄임

**상태:** 확정 · **대상:** Phase 1

- 직접 선택한 PVP 목표: 1,500
- 회사 누적 PVP 시작값: 700
- 이번 보름 신규 PVP 합계: 800

**기대 결과:** 개인 PVP 판정량 1,500, 추가 필요량 0, 개인 PVP 목표 달성.

### HALF-002 — 시작 PVP만으로 목표 초과 달성

**상태:** 확정 · **대상:** Phase 1

- 직접 선택한 PVP 목표: 1,500
- 회사 누적 PVP 시작값: 1,600
- 신규 PVP: 0

**기대 결과:** 개인 PVP 판정량 1,600, 추가 필요량 0. 목표를 다음 단계로 올리지 않는다.

### HALF-003 — 직접 선택한 목표 700

**상태:** 확정 · **대상:** Phase 1

- 직접 선택한 PVP 목표: 700
- 회사 누적 PVP 시작값: 800
- 신규 PVP: 0

**기대 결과:** 목표 700, 추가 필요량 0.

### HALF-004 — 일일 좌·우 시작 잔액은 선택한 보름 목표를 줄이지 않음

**상태:** 확정 · **대상:** Phase 1

- 일일 시작 잔액: `L 362 / R 261`
- 보름 동안 신규 원본 좌·우: 모두 0
- 보름 PVP 판정량: 0

**기대 결과:** 보름 원본 좌·우는 `0/0`이고 양쪽 목표는 모두 미달이다. 시작 잔액을 더해 `362/261`로 판정하면 오답이다.

### HALF-005 — 보름 마감 PVP가 작은 쪽을 채움

**상태:** 확정 · **대상:** Phase 1

- 이번 보름 신규 PVP 합계: 400
- 회사 누적 PVP 시작값: 0
- 보름 원본 좌: 2,500
- 보름 원본 우: 2,100

### HALF-006 — PVP를 동률 좌·우로 나눌 수 없음

## 7. 수당 발생일, 환산 횟수와 목표별 분포 선호

### COUNT-001 — 어떤 단계든 발생한 날짜 한 번으로 계산

**상태:** 확정 · **대상:** Phase 1

서로 다른 8일의 단계가 `[300, 300, 700, 1,500, 2,400, 6,000, 20,000, 60,000]`이면 커미션 발생일 수는 8이다.

6,000 이상 단계의 수당 환산표는 미확정이므로 이 전체 기간의 `commissionEquivalentUnits`는 `null`이다. 발생일 8일을 환산 8회라고 표시하면 오답이다.

### COUNT-002 — 한 날짜에 여러 임계값을 넘어도 한 번

**상태:** 확정 · **대상:** Phase 1

한 날짜의 판정 좌·우가 모두 60,000이면:

- 기록 단계는 60,000 하나다.
- 발생일 수 증가는 1이다.
- 300부터 60,000까지 7회로 세면 오답이다.

### COUNT-003 — 환산 6회는 보름 목표 실패가 아님

**상태:** 확정 · **대상:** Phase 1/4

8회 권장 대상 회원이 보름 PVP와 좌·우 목표를 모두 충족하고 300단계 커미션을 서로 다른 6일에 받으면:

- 발생일 수는 6으로 표시한다.
- 300단계 기준 환산 횟수도 6회이며 환산 8회 권장 미달을 표시할 수 있다.
- 프로젝트의 필수 보름 목표 실패로 처리하지 않는다.

### COUNT-004 — 확정 단계의 1·2·4·8 환산

**상태:** 확정 · **대상:** Phase 1/4

한 회원이 서로 다른 4일에 `[300, 700, 1,500, 2,400]` 단계를 받는다.

**기대 결과:** 수당 발생일은 4일이고 300단계 기준 환산 횟수는 `1+2+4+8=15회`다. 700단계를 4일 받는 다른 회원은 발생일 4일, 환산 8회이므로 목표 700의 환산 8회 권장에 도달한다.

### COUNT-P01 — 목표값과 구조별 수당 환산 미달 대상

**상태:** 확정 · **대상:** Phase 1/4

루트와 여러 깊이의 목표 700·1,500·2,400 회원을 함께 둔다. 일부 회원의 화면 찾기 표지판은 실제 깊이 및 목표값과 일부러 다르게 입력한다.

**기대 결과:**

- 목표 1,500·2,400 회원: 루트를 제외하고 첫 번째 완전한 내림차순 환산 미달 vector로 비교한다.
- 목표 700 회원: 루트를 제외하고 두 번째 완전한 내림차순 환산 미달 vector로 비교한다.
- 조직 깊이와 화면 표지판을 바꾸어도 집단, 이론상 상한, 목적 vector는 바뀌지 않는다.
- 각 회원의 이론상 환산 상한은 순수 재귀 최소 목표 총량과 시작 좌·우 잔액으로 계산하며, `미달=max(0,상한-실제 환산 횟수)`다.
- 루트는 두 환산 vector 모두에서 제외하고 별도 `U` 목표만 정상 커미션 발생일로 센다.
- 이론상 상한은 날짜별 배치 가능성의 증명이 아니다. 미달을 하드 실패로 처리하거나 이를 위해 신규 PV를 추가하지 않는다.
- 목표 700의 환산 8회 이상 회원 수와 총 환산 횟수는 화면 통계로 표시할 수 있지만 별도 comparator 단계가 아니다.

## 8. 자동 계획 정답 사례

이 절은 Phase 4에서 구현한다. Phase 1 계산 코어는 후보 결과를 재계산하는 데 사용한다.

별도 언급이 없는 두 자동 후보 비교는 `rootCommissionGoalShortfallDays`가 서로 같다고 가정한다. Policy·objective `7.0.0`은 총 신규 PV를 먼저 최소화하고, 같은 최소 비용 후보 안에서 맨 위 회원 목표 미달 일수를 최소화한다.

### OPT-P01 — 13영업일 단일 루트의 총량상 8일 목표와 8일 분산

**상태:** 확정 · **대상:** Phase 4

전제:

- 한 회원만 있고 양쪽 모두 `SELF`다.
- 회사 누적 PVP와 일일 좌·우 시작값은 모두 0이다.
- 회원의 PVP 목표로 700을 직접 선택한다.
- D1~D13은 반월의 모든 영업일이고 중간 일요일 행은 모두 0이다.
- 최소 보름 계획의 총량 profile은 신규 `P=700`, 원본 `L=1,800`, `R=2,500`이다. PVP 700은 보름 판정에서 작은 왼쪽에 적용되어 assessed 좌·우를 2,500/2,500으로 만든다.

후보 계획:

| 날짜 | P | SELF L | SELF R | 일일 결과 |
|---|---:|---:|---:|---|
| D1 | 300 | 0 | 300 | 당일 자격 300 도달, 정확히 300 단계 full commission |
| D2~D5, 각 날짜 | 100 | 200 | 300 | 매일 정확히 300 단계 full commission |
| D6~D8, 각 날짜 | 0 | 100 | 100 | D8에 누적 300/300으로 full commission |
| D9~D11, 각 날짜 | 0 | 100 | 0 | 한쪽 실적만 이월 |
| D12 | 0 | 100 | 400 | 누적 400/400으로 full commission |
| D13 | 0 | 300 | 300 | 이 후보의 여덟 번째 300 단계 full commission |
| **합계** | **700** | **1,800** | **2,500** | **커미션 8일** |

보름 마감에 PVP 700을 작은 쪽 왼쪽에 적용하면 `2,500/2,500`이다. 총 신규 PV는 `700 + 1,800 + 2,500 = 5,000`이다.

총량상 커미션 일수 상한:

- `N=13`, opening은 0이다.
- `n=8`이면 `floor(1,800/300)+floor(2,500/300)=14>=8`이고, 부족량은 `600+0<=P700`이다.
- `n=9`이면 부족량이 `900+200=1,100>P700`이므로 불가능하다.
- 따라서 총량상 운영 목표 `U=8`이고 위 후보의 실제 정상 커미션도 8일이라 `rootCommissionGoalShortfallDays=0`이다.

모든 직접 입력은 0 또는 100의 배수이며 D1은 당일 직접 PVP 300을 먼저 자격 누계에 포함하므로 허용된다. 여덟 번은 D1~D13에 분산되어 있지만 D13 자체는 특례나 필수 날짜가 아니다. 이 표는 총량상 목표를 달성한 검증 가능한 후보이지, exact backend 없이 모든 후순위 목적까지 최적임을 주장하는 증명은 아니다.

### OPT-001 — 한쪽 자식 조직에서 하위 실적 공동 활용

**상태:** 확정 · **대상:** Phase 4  
**검증 범위:** 목적 1인 총 신규 PV 하한과 보름 목표만 검증. 날짜별 최적 일정은 별도 사례에서 검증한다.

조직과 시작값:

- 회원 A의 왼쪽 자식은 회원 B다. 두 회원의 PVP 목표는 각각 700이다.
- A의 오른쪽과 B의 양쪽은 `SELF`다.
- 모든 시작값은 0이다.

최소 원본 합계 한 가지:

| 회원 | 신규 P | SELF L | SELF R | 설명 |
|---|---:|---:|---:|---|
| B | 700 | 1,800 | 2,500 | B 마감 PVP를 왼쪽에 적용하여 `2,500/2,500` |
| A | 700 | 입력 불가 | 1,800 | A 왼쪽은 B의 서브트리 총 5,000, PVP를 오른쪽에 적용 |

기대 결과:

- B의 개인 PVP와 좌·우 목표 달성
- A의 원본 왼쪽 5,000, 원본 오른쪽 1,800, 마감 오른쪽 2,500
- A의 개인 PVP 목표 달성
- 총 신규 PV `5,000 + 700 + 1,800 = 7,500`

최소성은 B 자체에 최소 5,000, A 자신의 PVP에 최소 700, A 오른쪽과 PVP 합에 최소 2,500이 필요하다는 하한으로 확인한다.

### OPT-002 — 양쪽 자식이 루트의 좌·우 목표를 함께 충족

**상태:** 확정 · **대상:** Phase 4  
**검증 범위:** 목적 1인 총 신규 PV 하한과 보름 목표만 검증. 날짜별 최적 일정은 별도 사례에서 검증한다.

- 루트 A의 왼쪽 자식은 B, 오른쪽 자식은 C다.
- B와 C의 PVP 목표는 700이며 양쪽 `SELF`, 모든 시작값은 0이다.

기대 최소 총 신규 PV:

- B 목표 최소 5,000
- C 목표 최소 5,000
- A 자신의 PVP 목표 700
- 전체 최소 10,700

A의 원본 좌·우는 각각 자식 서브트리 5,000이므로 별도 좌·우 직접 입력 없이 2,500 목표를 충족한다. A의 PVP 700은 하위 회원의 개인 PVP 목표를 대신하지 않는다.

### OPT-003 — 6,000 이상을 만들기 위한 추가 PV 금지

**상태:** 확정 · **대상:** Phase 4

- 후보 A는 총 신규 PV 5,000으로 모든 보름 목표를 충족하고 일일 최고 단계가 300이다.
- 후보 B는 같은 보름 목표를 충족하지만 어느 날 6,000 단계를 만들기 위해 총 신규 PV를 늘린다.

**기대 선택:** 후보 A. 더 높은 일일 단계 자체는 총 신규 PV 증가를 정당화하지 않는다.

하위 조직의 필수 실적만으로 자연스럽게 6,000·20,000·60,000에 도달하면 해당 공식 단계를 그대로 표시한다.

### OPT-004 — 30 이상 정확 보정이 구매를 줄이면 100단위보다 우선

**상태:** 확정 · **대상:** Phase 4

- 일일 시작 잔액: `P0/L362/R261`
- 그날 오른쪽 `SELF`에 추가할 수 있다.

| A | 39 | `362/300` | 300 | 39 |

**기대 선택:** 후보 A. 39는 자동 최소 직접값 30 이상이므로 허용되며, 100단위 가독성보다 신규 PV 61 절감이 우선이다.

### OPT-005 — 총 PV가 같을 때 100단위 선호

### OPT-006 — 8회를 위해 신규 PV를 추가하지 않음

**상태:** 확정 · **대상:** Phase 4

- 후보 B: 같은 목표 충족, 총 신규 PV `X + Y`이고 `Y > 0`, 수당 환산 8회

**기대 선택:** 후보 A. 8회 미달은 허용되며 추가 구매보다 최소 신규 PV가 우선이다.

### OPT-P02 — 환산 8회 초과가 가능한 동률 계획

**상태:** 확정 · **대상:** Phase 4

총 신규 PV, root shortfall, known payout, 초과 소멸량과 비교 대상보다 앞선 공평성 vector가 같은 두 후보 중 한 회원의 수당 환산 횟수는 8회, 다른 후보는 9회다.

두 회원의 이론상 상한이 같고 다른 조건도 같다면 환산 9회 후보의 미달이 8회 후보보다 작으므로 **환산 9회 후보를 선택한다**. 8회는 하드 cap이나 별도 threshold objective가 아니며, 9회를 만들기 위해 총 신규 PV를 늘리거나 known payout 등 높은 목적을 악화시킬 수는 없다.

### OPT-P03 — 초과 소멸량 점수

**상태:** 확정 · **대상:** Phase 4

- 일일 정산 전 값: `P500/L0/R300`
- PVP 적용 후 판정: `L500/R300`
- 달성 단계: 300, 정산 후 세 잔액 0

**기대 점수:** `500 + 0 + 300 - 2×300 = 200`이다. 단계에 필요한 600은 손실로 보지 않고, 실제 정산에서 함께 지워진 초과분 200만 센다.

이 수식은 qualification-valid `FULL_COMMISSION` 날짜에만 적용한다. 미발생·skip 날짜는 0이고, 자격 미달 기계적 정산은 자동 후보 자체가 무효다. 기간 말 carry는 CARRY-001처럼 실제 초기화 이벤트가 없으면 이 점수에 넣지 않는다.

### OPT-P04 — 여러 상위 목표에 대한 공동 기여 점수

**상태:** 확정 · **대상:** Phase 4

두 완전한 후보는 하드 제약과 직접 셀 하나의 100 PV 위치를 제외한 조건이 같으며 총 신규 PV, root shortfall, known payout와 초과 소멸량도 같다.

- 후보 A: 깊은 하위 `SELF`에 둬 아직 부족한 두 상위 회원의 같은 경로 목표에 각각 100씩 기여한다.
- 후보 B: 상위 회원 자신의 `SELF`에 둬 한 회원의 목표에만 100 기여한다.
- 공통 나머지 계획 때문에 두 후보 모두 최종 목표는 충족한다.

**기대 결과:** 공동 기여 횟수·양이나 트리 깊이는 독립 목적함수가 아니다. 하위 배치가 여러 상위 목표를 함께 채워 총 신규 PV를 줄이면 OPT-001/OPT-002처럼 목적 1에서 이긴다. 이 사례처럼 총 신규 PV를 포함한 앞선 목적이 이미 같으면 공동 기여만으로 후보 A를 선택하지 않고 root shortfall, known payout, 초과 소멸량, 목표군 환산 미달 vector, 미래 PVP 투자, 100단위, 최대 직접 PVP, 결정적 배정 벡터 순서로 계속 비교한다.

### OPT-P05 — 완전 동률 계획의 결정적 타이브레이커

**상태:** 확정 · **대상:** Phase 4

모든 앞선 목적 점수가 같은 두 계획이 있고 유일한 차이는 동일한 100 PV를 D2에 둘지 D3에 둘지다.

직접 편집 셀을 다음 순서로 평탄화한다.

1. ISO 영업일 오름차순
2. Phase 2의 stable `memberKey`와 조직 topology에서 만든 정본 회원 순서
3. 필드 `PVP`, `SELF_LEFT`, `SELF_RIGHT`

첫 번째로 다른 좌표에서 더 큰 값을 더 이른 좌표에 둔 계획을 선택한다. 따라서 **D2에 100을 둔 계획이 이긴다**. 이 완전한 배정 벡터는 정확한 마지막 목적 단계이며 솔버 변수 순서에 우연히 맡기지 않는다.

### OPT-007 — 자식보다 부모에 둔 PVP 100이 소멸량을 줄임

**상태:** 확정 · **대상:** Phase 4

### OPT-008 — 자식이 PVP 100을 필요로 하면 하위 배치가 총 PV를 줄임

### OPT-019 — 동적 영업일 수와 맨 위 회원 총량상 목표

**상태:** 확정 · **대상:** Phase 4

`C0(L,R,P,M)`은 `0<=n<=M` 중 `floor(L/300)+floor(R/300)>=n`과 `MAX(0,300n-L)+MAX(0,300n-R)<=P`를 모두 만족하는 최대 `n`이다. 시작 좌·우 잔액은 `L/R`에 더하지 않고 첫 qualification-valid full commission의 소비·reset 한 번으로만 계산한다.

#### OPT-019A — 총량상 13영업일 모두 가능

- 실제 입력 가능 영업일 수 `N=13`
- 일일 시작 잔액 0, 최소 총량 `L=3,900`, `R=3,900`, `P=0`

**기대 결과:** `U=C0(3,900,3,900,0,13)=13`이다. 총 신규 PV가 같은 후보끼리 루트 정상 커미션 13일 후보의 shortfall은 0이고 12일 후보는 1이므로 13일 후보가 이긴다. 13일을 만들기 위해 총 PV를 더 써야 한다면 더 적게 쓰는 12일 후보가 목적 1에서 이긴다.

#### OPT-019B — 14영업일 달력

- 실제 입력 가능 영업일 수 `N=14`
- 일일 시작 잔액 0, 최소 총량 `L=4,200`, `R=4,200`, `P=0`

**기대 결과:** `U=14`다. 앱이 13으로 고정하면 오답이며 루트 목표·실제·shortfall 표시와 comparator가 모두 14를 기준으로 한다.

#### OPT-019C — 총량 부족 조직의 이론상 최대 8일

- `N=13`, opening 0, `L=1,800`, `R=2,500`, `P=700`

**기대 결과:** OPT-P01 계산대로 `U=8`이다. 8일 후보는 목표 달성이며 9일을 하드 요구해 요청을 불가능으로 만들면 오답이다.

#### OPT-019D — 시작 잔액은 첫 reset 한 번에만 사용

- `N=13`, 누적 PVP 시작값과 선택 목표는 700이므로 `P=0`
- 기간 최소 원본 총량은 `L=2,500`, `R=2,500`
- 일일 시작 잔액은 `O_L=300`, `O_R=300`

**기대 결과:** opening이 없으면 `C0(2,500,2,500,0,13)=8`이다. 시작 잔액 300:300으로 첫날 full commission 한 번을 추가한 뒤 잔액이 모두 reset되고, 남은 신규 총량으로 8회를 만들 수 있으므로 `U=9`다. opening을 기간 총량에 더해 여러 날짜에 재사용하거나 10회 이상으로 계산하면 오답이다.

#### OPT-019E — Constructive shortfall은 경고 가능한 verified fallback

- 총량상 `N=U=13`인 요청에서 constructive generator가 루트 full commission 12일인 후보만 찾는다.
- 후보는 보름 PVP·좌·우, qualification, lifetime cap, Sunday zero와 자동 직접값 0 또는 30 이상을 모두 충족한다.

**기대 결과:** 후보를 버리지 않고 `rootCommissionGoalShortfallDays=1`인 verified shortfall candidate로 제공하며 `맨 위 회원 전체 영업일 목표 미달 1일`을 표시한다. 이후 같은 최소 총 PV의 13일 후보를 찾으면 shortfall 0이므로 교체한다. 13일 후보가 더 많은 PV를 쓰면 교체하지 않는다.

#### OPT-019F — 목표 후보 미발견은 `INFEASIBLE` 증명이 아님

**기대 결과:** Constructive 종료, 휴리스틱 실패, 제한 시간 동안 shortfall 0 후보를 찾지 못한 사실만으로 `INFEASIBLE`을 반환하지 않는다. 사용 가능한 shortfall 후보가 있으면 `TIME_LIMIT/CANCELLED/FAILED` 상태에서 보존하고, 없으면 후보 없는 해당 상태를 반환한다. `INFEASIBLE`은 일치하는 certified exact model의 완전 증명에만 허용한다.

### OPT-P06 — 최적화 목적함수 합계의 범위

**상태:** 설계 계약 · **대상:** Phase 4/5

각 직접 셀은 허용 범위 안이지만 전체 후보의 총 신규 PV 또는 재시뮬레이션 점수 합계가 선택한 정수 표현 범위를 넘는다.

**기대 결과:** 부동소수점 반올림, 거대한 가중합 또는 가중치 포화 상태로 후보 순서를 정하지 않는다. 총 신규 PV, `rootCommissionGoalShortfallDays`, known payout, 초과 소멸량, 환산 미달 vector, 미래 투자와 각 파생 합계에 checked integer 연산을 사용한다. 모델 생성 전에 솔버의 정확한 정수 범위를 검증하고 하나라도 표현할 수 없으면 명시적인 `OPTIMIZATION_SCORE_OUT_OF_RANGE` 오류를 반환한다. 목적 단계는 `objectiveVersion=7.0.0` 순서대로 각각 정확히 고정한다.

### MODEL-001 — 모델 해는 정본 엔진에 대해 sound해야 함

**상태:** 설계 계약 · **대상:** Phase 4

테스트 모델이 Sunday nonzero, 연결된 `CHILD` 방향 직접값 또는 자격 299의 기계적 정산을 포함한 벡터를 해로 반환한다.

**기대 결과:** 정본 shape/numeric 검증과 `rulesetVersion=8.0.0` 계산이 후보를 거부한다. raw 솔버 벡터에는 candidate ID를 부여하지 않고 화면·checkpoint·apply 경계로 내보내지 않는다. 솔버가 feasible이라고 보고했다는 이유로 `OPTIMAL`을 표시하면 오답이다.

### MODEL-002 — 유효한 더 나은 배정을 누락하면 completeness 실패

**상태:** 설계 계약 · **대상:** Phase 4

테스트 모델이 1 PV 단위 유효 배정, 특정 날짜 또는 OPT-007의 부모 PVP 배치를 임의의 domain restriction으로 제외하고 남은 공간을 완전 탐색했다고 보고한다.

**기대 결과:** model certificate의 completeness/equivalence 검사가 실패한다. 찾은 후보를 Phase 1로 검증해 사용할 수는 있지만 `OPTIMAL`이나 `INFEASIBLE`을 주장할 수 없다. 작은 oracle에 더 낮은 유효 후보가 있으면 반드시 불일치로 검출한다.

### MODEL-003 — 모델 점수와 정본 목적 벡터가 다르면 objective preservation 실패

**상태:** 설계 계약 · **대상:** Phase 4

솔버가 한 후보의 `rootCommissionGoalShortfallDays`, 초과 소멸량, high-target 미달 벡터, target-700 미달 벡터, `nonHundredCellCount`, `maxDirectPvp` 또는 결정적 배정 벡터를 정본 재계산과 다르게 보고한다.

**기대 결과:** `objectiveVersion=7.0.0` 정본 evaluator의 값만 권위가 있으며 후보를 model-consistency failure로 거부한다. 솔버 점수를 덮어써서 usable candidate로 계속 사용하거나 낮은 목적 단계로 진행하면 오답이다.

### MODEL-004 — model certificate와 활성 버전의 정확한 결합

**상태:** 설계 계약 · **대상:** Phase 4

`ModelCertificate 4.0.0`은 최소한 모델 구현, 계산 규칙·엔진 `8.0.0`, 정책·목적 `7.0.0`, 달력/fingerprint 버전, 솔버 adapter와 버전, exact integer·tolerance 조건, soundness/completeness/objective-preservation 증거 모음을 식별한다.

**기대 결과:** 활성 요청과 certificate의 식별자 중 하나라도 다르면 proof 상태를 사용할 수 없다. 후보는 현재 버전으로 독립 재검증될 때만 unproven candidate로 사용할 수 있으며, 이전 certificate의 `OPTIMAL`·`INFEASIBLE`을 승계하지 않는다.

### STATUS-001 — 휴리스틱 종료는 최적·불가능 증명이 아님

**상태:** 설계 계약 · **대상:** Phase 4

구성 알고리즘이나 휴리스틱이 유효 후보 한 개를 찾은 뒤 더 탐색할 노드가 없다고 자체적으로 종료하지만 certified exact proof는 없다.

**기대 결과:** independently verified unproven candidate로만 표시한다. `OPTIMAL` 또는 `INFEASIBLE`을 반환하면 오답이다.

### STATUS-002 — `OPTIMAL`과 `INFEASIBLE`의 완전 증명 조건

**상태:** 설계 계약 · **대상:** Phase 4

- `OPTIMAL`은 총 신규 PV부터 완전한 결정적 배정 벡터까지 모든 scalar/vector 단계가 certificate 조건 아래 정확히 증명되고 최종 후보가 독립 검증된 경우에만 반환한다.
- `INFEASIBLE`은 같은 certified model이 허용된 전체 배정 공간에 유효 후보가 없음을 완전 증명한 경우에만 반환하며 candidate는 null이다.
- deadline, 취소, 솔버 실패, 아직 후보를 찾지 못함 또는 primary bound만 일치함은 `INFEASIBLE`이 아니다.

### STATUS-003 — wall-clock 종료 후보의 정직한 결정성 범위

**상태:** 설계 계약 · **대상:** Phase 4

같은 fingerprint를 두 번 실행한다.

**기대 결과:** 완전 증명된 `OPTIMAL`은 OPT-P05 때문에 allocation과 목적 벡터가 byte-for-byte 같다. 실제 wall-clock `TIME_LIMIT`, `CANCELLED`, `FAILED`의 incumbent는 매번 독립 검증되어야 하지만 byte equality를 보장하지 않는다. 반복 가능한 중간 결과가 필요한 테스트는 wall clock 대신 deterministic work/node budget 또는 fake clock을 사용한다.

### STATUS-004 — 제품 실행 한도는 한 번의 고정 30분

**상태:** 설계 계약 · **대상:** Phase 4

- 제품 deadline은 `1,800,000ms` 하나이며 3시간·사용자 지정·숨은 연장 모드는 없다.
- deadline 전에 완전 증명이 끝나면 `OPTIMAL`을 반환한다.
- deadline에 verified candidate가 있으면 그 후보를 보존한 `TIME_LIMIT`, 없으면 candidate가 null인 `TIME_LIMIT`을 반환한다.
- 이후 `다시 계산`은 선택한 verified warm start를 사용할 수 있는 새로운 30분 실행이며 이전 proof frontier를 이어받았다고 표시하지 않는다.

deadline 소진을 `OPTIMAL`, `INFEASIBLE` 또는 백그라운드 계산 계속으로 표현하면 오답이다.

## 9. 실제값과 부분 재시뮬레이션 사례

### RESIM-001 — 실제 완료일까지 고정하고 미래만 변경

**상태:** 확정 · **대상:** Phase 5

- 대상 기간: 1일~15일
- 1일~6일 실제 원본이 확정되었다.
- 6일 실제값이 확정 계획과 다르다.

**기대 결과:**

- 1일~6일의 직접 실제 원본은 어떤 후보에서도 변경되지 않는다.
- 1일~6일 일일 잔액과 보름 누계를 실제값으로 처음부터 다시 계산한다.
- 7일 시작 잔액은 6일 실제 정산 결과다.
- 결정 변수는 7일~15일 미래 직접 입력뿐이다.

### RESIM-P01 — 실제값의 빈칸과 명시적 0

**상태:** 정답 보류 — Q-RESIM-02 · **대상:** Phase 5

6일의 한 회원에 `P = 0`, `SELF L = null`, `SELF R = 100`이 입력되어 있다.

확정할 정답:

- `P = 0`은 실제 0으로 고정한다.
- `SELF L = null`을 확정 계획 복사값, 미완료, 또는 오류 중 무엇으로 볼지 결정한다.
- 일부 셀만으로 6일 전체를 실제 완료 처리할 수 있는지 결정한다.

### RESIM-P02 — 목표 회복과 변경 최소화의 순서

**상태:** 정답 보류 — Q-RESIM-01 · **대상:** Phase 5

- 후보 A는 미래 변경 셀이 0이지만 보름 좌 목표가 미달이다.
- 후보 B는 미래 셀 1개를 바꾸고 보름 목표를 회복한다.

**제안 기대 선택:** 후보 B. 보름 목표 회복을 하드 제약으로 두고, 유효한 후보 사이에서만 변경 셀 수를 비교한다.

### RESIM-P03 — 변경 셀 수는 직접 입력만 계산

**상태:** 정답 보류 — Q-RESIM-03 · **대상:** Phase 5

하위 B의 `SELF L` 한 셀을 바꾸어 B와 상위 A·루트의 파생 좌·우 여러 칸이 달라진다.

**제안 기대 결과:** 변경 직접 입력 셀 수는 1, 변경 회원 수는 1이다. 파생 결과 셀은 차이로 표시하되 최적화의 변경 셀·회원 수에는 넣지 않는다.

### RESIM-P04 — 일일 커미션 결과 재확보의 의미

**상태:** 정답 보류 — Q-RESIM-04 · **대상:** Phase 5

두 후보 모두 보름 필수 목표와 더 높은 재시뮬레이션 목적 점수가 같다.

- 기준 미래안: D8에 700 단계 한 번.
- 후보 A: D8에 700 단계 유지.
- 후보 B: D9에 700 단계 한 번.
- 별도 후보 C: D8에 300 단계 한 번.

같은 날짜·단계를 유지해야 하는지, 발생일 수만 같으면 되는지, 어느 미래 날짜든 커미션 기회를 확보하면 되는지 답으로 선택 기준을 고정한다.

### RESIM-P05 — 여러 번 재시뮬레이션할 때 기준 미래안

**상태:** 정답 보류 — Q-RESIM-03 · **대상:** Phase 5

1. 최초 확정 계획에는 D8의 한 셀이 0이다.
2. 첫 재시뮬레이션이 D8을 100으로 바꾸고 이 계획을 다시 회원에게 전달했다.
3. 이후 다른 실제값 때문에 두 번째 재시뮬레이션을 실행한다.

두 번째 변경 셀 수를 최초 확정안의 0과 비교할지, 직전 재전달안의 100과 비교할지 확정한다. 선택한 기준 리비전 ID를 결과에 기록해야 한다.

### RESIM-P06 — 미래 영업일이 없어 목표 회복 불가

**상태:** 정답 보류 — Q-RESIM-01 · **대상:** Phase 5

- 마지막 영업일까지 실제값이 확정되어 미래 결정 변수가 없다.
- 한 회원의 보름 왼쪽 목표가 200 부족하다.

**제안 기대 결과:** 과거 실제값을 바꾸지 않고 `INFEASIBLE`을 반환하며 해당 회원·왼쪽·부족량 200을 표시한다. 부족한 계획을 성공으로 저장하거나 과거 실제값을 수정하면 오답이다.

### RESIM-P07 — 추가 신규 PV의 두 계산 방식

**상태:** 정답 보류 — Q-RESIM-03 · **대상:** Phase 5

- 기준 미래안 두 셀: `[100, 0]`
- 후보 두 셀: `[0, 100]`

| 방식 | 추가 신규 PV |
|---|---:|
| 총합 순증 `MAX(0, 100-100)` | 0 |
| 셀별 증가분 합 `MAX(0,0-100)+MAX(0,100-0)` | 100 |

어느 수식을 목적함수에 사용할지 답으로 고정한다. 변경 셀 수는 두 방식 모두 2다.

### VAL-002 — 반월 밖 날짜

### VAL-003 — 중복 회원 ID

**상태:** 설계 계약 · **대상:** Phase 1

### VAL-004 — 개별 입력은 안전하지만 파생 합계가 범위를 넘음

**상태:** 설계 계약 · **대상:** Phase 1

- JavaScript 안전한 정수 최댓값을 `M = 9,007,199,254,740,991`로 둔다.
- A의 왼쪽 자식 B에 `P = M`, A의 오른쪽 자식 C에 `P = 1`을 입력한다.
- 두 개별 입력은 각각 안전한 정수 범위 안이다.
- A의 `T = M + 1`은 안전한 정수 범위를 넘는다.

**기대 결과:** 반올림된 합계를 반환하지 않고 `PV_AGGREGATE_OUT_OF_RANGE` 오류로 전체 계산을 실패시킨다.

### VAL-006 — 회원별 시작값 완전성

**상태:** 설계 계약 · **대상:** Phase 1

- 조직 스냅샷에 회원 A와 B가 있다.
- 회사 누적 PVP를 qualification·보름 역할로 매핑한 값과 일일 `P=0/L/R`의 다섯 필드를 가진 OpeningState는 A에만 있고 B에는 없다.

**기대 결과:** `OPENING_STATE_MISSING` 오류를 B 위치와 함께 반환한다. 조직에 없는 회원의 OpeningState가 추가로 있으면 `OPENING_STATE_MEMBER_NOT_FOUND` 오류다. 한 회원의 다섯 필드 중 하나가 없거나 `openingQualificationPvp !== fortnightPvpOpeningCredit`, `dailyCarryPvp !== 0`, 누적값이 2,400 초과이면 완전한 `8.0.0` 제품 입력이 아니다.
