# Phase 2 실행 계획 — 프로젝트와 조직 입력

작성일: 2026-07-11  
상태: 실행 계획 작성 완료 — 진입 결정 대기

이 문서는 `ROADMAP.md`의 **Phase 2 — 프로젝트와 조직 입력**을 실제 구현 작업으로 분해한다. `TECHNICAL_DESIGN.md`, `pyramid-app-requirements-v2.md`, 완료된 Phase 1 공개 계약을 기준으로 하며, Phase 3 이후 기능은 포함하지 않는다.

## 1. Phase 2의 목적

Phase 2의 목적은 처음으로 사용할 수 있는 입력 화면을 만들고, 반월 프로젝트의 기간·회원·조직 배치·네 종류의 시작값을 정확히 입력하게 하는 것이다.

화면에서 편집 중인 값은 비어 있거나 일시적으로 잘못될 수 있다. 따라서 UI 초안을 Phase 1 계산 입력으로 바로 사용하지 않고, 다음 두 계층을 분리한다.

1. 불완전한 상태를 허용하는 인메모리 편집 초안
2. 검증과 정규화가 끝난 불변 프로젝트 설정 전달 객체

Phase 2가 만드는 최종 결과는 **인메모리 `PlanProject`와 Phase 1 계산용 `OrganizationSnapshotInput`을 묶은 프로젝트 설정 전달 객체**다. Phase 3는 여기에 날짜별 직접 배정값을 붙인다. 날짜별 배정값은 Phase 3 범위이므로 Phase 2만으로 완전한 `CalculatePlanInput`을 만들거나 계산 결과를 표시하지 않는다.

## 2. 성공 조건

Phase 2는 다음 상태를 목표로 한다.

- 연·월과 상반기·하반기를 선택해 새 프로젝트 초안을 만들 수 있다.
- 프로젝트 제목은 기간에서 기본값을 제안하며 필요하면 수정할 수 있다.
- 프로젝트는 Phase 2에서 인메모리 `IN_PROGRESS` 상태로 만들어지고 현재 조직 입력 스냅샷을 참조한다.
- 회원 ID·이름·레벨과 부모 기준 좌·우 위치를 입력하고 수정할 수 있다.
- 피라미드 그림에서 루트, 회원, 비어 있는 좌·우 슬롯, 파생된 `CHILD/SELF` 방향을 구분할 수 있다.
- 회원마다 보름 PVP 시작값과 일일 PVP·좌·우 잔액을 서로 다른 네 입력란에 입력할 수 있다.
- 빈값과 명시적인 숫자 `0`이 구분된다.
- 중복 회원 ID, 중복 슬롯, 부모 누락, 순환, 복수 루트, 고아 회원과 잘못된 숫자를 계산 전에 위치가 있는 오류로 보여 준다.
- `ERROR`가 있는 초안에서는 정규 결과를 만들지 않고 다음 단계 진입을 막는다. `WARNING`은 보존해 표시하되 완료를 차단하지 않는다.
- 유효한 초안만 Phase 1의 `OrganizationSnapshotInput` 계약으로 변환된다.
- 입력 완료 뒤 초안을 다시 수정하면 준비 상태와 현재 활성 전달 객체가 즉시 해제되고, 다시 검증해야 한다.
- 새 프로젝트는 이전 프로젝트의 회원·조직·시작값을 자동으로 가져오지 않는다.
- 새로고침 복구나 영구 저장이 없다는 현재 제한을 화면에서 알 수 있다.
- Phase 1 계산 테스트와 커버리지 기준을 낮추거나 깨뜨리지 않는다.
- 타입 검사, 전체 테스트, 커버리지 검사, 프로덕션 빌드와 빌드 산출물 검사가 통과한다.

## 3. 구현 전 진입 게이트

### 3.1 완료된 기반

- Phase 1 결정론적 계산 코어와 자동 테스트가 완료되었다.
- `PeriodInput`, `MemberSnapshot`, `OpeningStateInput`, `OrganizationSnapshotInput`의 계산 계약이 구현되어 있다.
- 조직 불변조건과 PV 검증 규칙이 Phase 1의 `validation.ts`에 구현되어 있다.
- TypeScript, Vite, Vitest, CI와 GitHub Pages `/ngplan/` 빌드 경로가 구성되어 있다.
- 자동 최적화, 계획 리비전, 실제값, 저장 기능은 아직 구현되지 않았다.

### 3.2 착수 전에 확정할 결정

아래 항목은 계획서의 권장안을 J님과 확정한 뒤 구현한다.

| 결정 | 권장안 | 이유 |
|---|---|---|
| UI 프레임워크 | React + React DOM, 컴포넌트 테스트는 Testing Library 계열 | Phase 2의 트리·폼 상태와 Phase 3의 큰 작업표, Phase 5의 다중 상태 화면까지 확장하기 쉽다. |
| Phase 2 조직 변경 정책 | 계획 리비전이 아직 없는 인메모리 `IN_PROGRESS` 초안에서는 자유롭게 편집하고, 입력 완료 때마다 새 불변 계산용 조직 입력을 만든다. | Q-PRODUCT-02 전체를 미리 구현하지 않으면서 Phase 2 편집 범위를 명확히 한다. |
| 시작값 초기 상태 | 네 시작값 모두 빈칸으로 시작하고 사용자가 `0`을 포함해 명시적으로 입력하게 한다. | 빈값을 자동으로 0으로 바꾸거나 이전 프로젝트 값을 실수로 이월하는 일을 막는다. |
| 하위 회원이 있는 회원 삭제 | 삭제를 차단하고 먼저 하위 회원을 이동하거나 잎부터 삭제하게 한다. | 한 번의 조작으로 서브트리 전체가 사라지는 데이터 손실을 피한다. |
| 배치 조작 | 빈 좌·우 슬롯에서 회원 추가, 회원 편집 폼에서 부모·방향 변경을 지원한다. 드래그 앤 드롭은 제외한다. | 키보드 접근성과 원자적 오류 처리를 먼저 확보하고 시각 효과의 복잡도를 제한한다. |
| 제목과 기간의 관계 | 기간에서 만든 제안 제목을 사용자가 수정하기 전에는 기간 변경에 맞춰 갱신한다. 한 번 직접 수정한 제목은 기간이 바뀌어도 보존하고 `기본 제목 사용`으로 다시 연결한다. | 기간 수정이 사용자의 제목을 예고 없이 덮어쓰지 않게 한다. |
| 프로젝트 상태 | Phase 2에서는 `IN_PROGRESS`만 사용하고 `입력 준비 완료`는 검증 결과에서 파생한다. `CLOSED` 전환은 구현하지 않는다. | 종료 잠금·과거 보존은 Phase 6 책임이며, 준비 여부를 영구 상태처럼 저장할 필요가 없다. |

UI 프레임워크 결정은 `TECHNICAL_DESIGN.md`의 Q-STACK-01 후속 결정으로 기록한다. Q-PRODUCT-02는 Phase 2에 필요한 위 좁은 정책만 확정하고, 확정 계획·실제 리비전과 기존 스냅샷의 관계는 Phase 5 착수 전까지 미결정으로 남긴다.

`ROADMAP.md`의 Phase 2 결과인 `진행 상태 관리`는 이번 Phase에서 **인메모리 `IN_PROGRESS` 프로젝트와 검증에서 파생되는 준비 상태 관리**로 해석한다. 요구사항의 `CLOSED` 전환·읽기 전용 잠금과 기술 설계의 영구 상태 필드는 Phase 6에 구현한다. 이 Phase 배분은 PRE-WP0에서 `ROADMAP.md`와 `TECHNICAL_DESIGN.md`에 명시하여 완료 판정의 모호함을 없앤다.

### 3.3 진입 완료 기준

- UI 프레임워크와 DOM 테스트 환경이 확정되어 있다.
- Phase 2용 조직 변경 정책과 삭제 정책이 확정되어 있다.
- 빈 시작값과 명시적인 0의 처리 방식이 확정되어 있다.
- 기간 변경 뒤 사용자 제목을 보존하는 방식이 확정되어 있다.
- 프로젝트 상태와 저장 필드의 Phase별 책임이 `ROADMAP.md`와 `TECHNICAL_DESIGN.md`에 명시되어 있다.
- 결정 결과가 `TECHNICAL_DESIGN.md`와 당일 개발 로그에 반영되어 있다.
- Phase 2 구현 범위가 Phase 3 이후 기능을 포함하지 않는다는 점이 다시 확인되어 있다.

## 4. 포함 범위

### 4.1 프로젝트 초안

- 대상 연·월과 `FIRST_HALF/SECOND_HALF`
- 기간에서 제안되는 프로젝트 제목과 제목 수정
- 기본 시간대 `Asia/Seoul`
- 세션 안에서 안정적인 프로젝트 키
- 현재 계산용 조직 입력의 `snapshotId`를 참조하는 인메모리 `PlanProject`
- `PlanProject`의 `IN_PROGRESS` 편집 상태
- 검증 결과에서 파생되는 `편집 중/입력 준비 완료` 표시
- 새 프로젝트 시작과 현재 초안 초기화

### 4.2 회원과 조직 편집

- 세션 안에서 안정적인 `memberKey`
- 회사 회원 ID, 이름, 1 이상의 정수 레벨
- 루트 한 명
- 비루트 회원의 `parentMemberKey + sideAtParent`
- 빈 좌·우 슬롯에서 하위 회원 추가
- 회원 정보 수정, 부모·방향 이동, 잎 회원 삭제
- 부모의 좌·우 자식 인덱스와 `CHILD/SELF` 표시의 파생
- 피라미드 형태의 조직 시각화와 선택 상태

연결의 권위 원천은 계속 하위 회원의 `parentMemberKey + sideAtParent` 하나뿐이다. 부모 객체에 `leftChild/rightChild`를 별도 저장하지 않는다.

### 4.3 시작값 입력

- `fortnightPvpOpeningCredit`
- `dailyCarryPvp`
- `dailyCarryLeft`
- `dailyCarryRight`
- 빈 문자열, 잘못된 문자열, 유효한 0 이상 안전 정수의 구분
- 회원별 네 값의 독립 오류 표시

### 4.4 검증과 정규화

- 편집 중 불완전한 초안을 위한 필드·명령 검증
- 회원 추가·이동·삭제 명령의 원자적 성공 또는 실패
- Phase 1 조직·시작값 검증 로직을 재사용하는 공개 검증 계약
- UI 필드를 Phase 1 타입으로 변환하는 명시적 파서
- 유효한 경우에만 새 불변 프로젝트 설정 전달 객체 생성
- 오류 코드, `ERROR/WARNING`, 회원·필드·방향 위치, 설명과 수정 제안을 화면에 연결
- 정규화 전후 초안과 이전 전달 객체의 비변경 보장

### 4.5 기능 UI의 기본 품질

- 명시적인 입력 레이블과 도움말
- 키보드로 프로젝트 생성, 회원 선택, 추가·수정·이동·삭제 가능
- 오류 요약과 각 입력 오류의 연결
- 색만으로 상태를 구분하지 않는 표시
- 작은 화면에서는 폼과 조직도를 순서대로 사용할 수 있고, 큰 조직도는 안전하게 스크롤 가능
- `/ngplan/` 하위 경로의 정적 빌드에서 앱 진입 가능

Phase 2 UI는 실제 업무 흐름을 검증할 수 있는 기능 화면과 기본 접근성 기준까지 만든다. 전체 제품의 디자인 시스템, 고급 애니메이션, 최종 시각 완성도와 Phase 7의 정식 접근성·지원 브라우저 감사는 요구하지 않는다.

## 5. 제외 범위

- 날짜별 PVP·좌·우 직접 배정 입력
- 엑셀과 같은 가로형 계획 작업표
- 일일·보름 계산 결과 표시
- 자동 신규 PV 배정과 최적화
- 계획 후보 비교와 추천
- 확정 계획, 실제값, 리비전, 부분 재시뮬레이션
- `CLOSED` 전환, 종료 잠금, 과거 프로젝트 열람
- `localStorage`, `sessionStorage`, IndexedDB, 파일, 서버를 포함한 모든 영구 저장
- 자동 저장, 새로고침 복구, 계정, 동기화
- 이전 프로젝트 복제와 시작값 자동 이월
- 가져오기·내보내기, PDF·스프레드시트·인쇄
- 드래그 앤 드롭 조직 편집
- 다중 프로젝트 목록과 검색
- 자동 최적화용 Web Worker
- 사용자 도메인 연결과 프로덕션 운영 절차
- 정식 접근성 감사, 다중 브라우저 인증과 실제 규모 성능 검증

새로고침하면 현재 초안이 사라지는 것은 Phase 2의 알려진 제한이다. 이를 숨기기 위한 임시 브라우저 저장을 추가하지 않는다.

## 6. 아키텍처와 목표 파일 구조

### 6.1 계층 책임

| 계층 | 책임 | 금지 사항 |
|---|---|---|
| UI | 입력 표시, 사용자 이벤트, 오류 위치 연결, 조직 시각화 | 계산 규칙·조직 불변조건 재구현 |
| Application Draft | 불완전한 문자열 입력과 편집 명령, 세션 키, 선택 상태 | Phase 1 불변 타입인 척하는 강제 캐스팅 |
| Normalization | 문자열 파싱, 정규 객체 생성, 실패 결과 반환 | 빈 문자열을 암묵적으로 0으로 변환 |
| Phase 1 Domain | 기간, PV, 조직·시작값 불변조건의 정본 검증 | UI 상태와 DOM 의존성 |
| Phase 1 Engine | Phase 3 이후 완전한 배정값이 있을 때 계산 | Phase 2에서 가짜 0 배정표로 호출 |

UI 컴포넌트는 Phase 1 내부 모듈을 직접 호출하지 않는다. Application 계층이 공개 검증 계약과 정규화 경계를 감싸고, UI에는 명령 결과와 표시용 오류만 제공한다.

### 6.2 핵심 상태 계약

구체적인 이름은 구현 시 조정할 수 있지만 다음 역할은 분리한다.

| 계약 | 핵심 내용 |
|---|---|
| `ProjectSetupDraft` | 제목 문자열과 자동·사용자 수정 상태, 기간 입력 문자열·선택값, 회원 초안 목록, 현재 선택 회원 |
| `MemberDraft` | 안정 키, ID·이름·레벨 문자열, 부모 키·방향, 네 시작값 문자열 |
| `DraftCommandOutcome` | 성공한 새 초안 또는 기존 초안을 유지한 위치 있는 명령 오류 |
| `ProjectSetupValidation` | 필드 오류·경고, 조직 오류·경고, 전체 준비 가능 여부 |
| `NormalizeProjectSetupOutcome` | 성공 시 전달 객체와 경고, 실패 시 오류·경고만 반환하는 판별 가능한 결과 |
| `PlanProject` | Phase 2 인메모리 최소 정본인 프로젝트 키·제목·기간·시간대·`IN_PROGRESS`·현재 `organizationSnapshotId` |
| `ProjectSetupBundle` | `PlanProject`와 `OrganizationSnapshotInput`을 함께 Phase 3에 넘기는 전달 객체. 별도의 저장 정본이 아님 |

`memberKey`, `projectId`, `snapshotId`는 이름, 회사 회원 ID, 배열 인덱스에서 만들지 않는다. 키 생성기를 Application 계층에 주입하여 실제 화면에서는 유일 키를 만들고 테스트에서는 고정 키를 사용할 수 있게 한다.

이 문서의 `OrganizationSnapshotInput`은 현재 코드에 구현된 **Phase 1 계산 입력 DTO**를 뜻한다. `TECHNICAL_DESIGN.md`의 장기 저장용 `OrganizationSnapshot`에 있는 `createdAt`과 이력 메타데이터는 Phase 6 책임이며, Phase 2에서 두 번째 저장 모델을 만들지 않는다. 마찬가지로 `PlanProject`의 리비전 ID, 스키마 버전, 생성·수정 시각은 해당 기능이 필요한 후속 Phase에서 확장한다.

완료 게이트:

### WP2 — 프로젝트와 편집 초안 모델

**선행 조건:** WP1 완료  
**파일 범위:** `src/application/project-setup`, 프로젝트 기간 UI

작업:

1. 프로젝트·회원·시작값의 문자열 기반 Draft 타입을 만든다.
2. ID 생성기를 주입받는 새 프로젝트 팩토리를 만든다.
3. 팩토리가 이전 프로젝트나 이전 전달 객체를 인자로 받지 못하게 한다.
4. 연·월·반기에서 제목 기본값을 제안하고 사용자 수정 여부를 별도 상태로 유지한다.
5. 수정 전 제목만 기간 변경에 맞춰 갱신하고, 직접 수정된 제목은 보존한다.
6. `validatePeriod`가 성공한 `PeriodInput`만 날짜 파생 함수에 전달한다.
7. 새 프로젝트 동작이 현재 초안을 버린다는 확인 경계를 둔다.

완료 게이트:

- 새 프로젝트의 조직과 네 시작값이 항상 새 빈 상태다.
- 상반기·하반기와 28·29·30·31일 월말이 Phase 1 기간 계약과 일치한다.
- 빈 문자열을 숫자 0으로 해석하지 않는다.
- 기간을 바꿔도 직접 수정한 제목이 예고 없이 덮어써지지 않는다.

### WP3 — 회원·시작값 편집 명령

**선행 조건:** WP2 완료  
**파일 범위:** Application 편집 명령과 회원·시작값 폼

작업:

1. 루트 생성, 빈 슬롯 자식 추가, 회원 정보 수정 명령을 만든다.
2. 부모·방향 이동을 한 번의 원자적 명령으로 처리한다.
3. 점유 슬롯, 자기 자신을 부모로 지정, 자기 후손 아래 이동을 거부한다.
4. 잎 회원 삭제를 지원하고 하위 회원이 있으면 삭제를 차단한다.
5. 회사 회원 ID·이름·레벨의 필수값과 중복을 검증한다.
6. 네 시작값을 독립 문자열 필드로 편집하고 각 필드를 개별 파싱한다.
7. 실패한 명령이 원래 초안과 현재 유효한 배치를 변경하지 않는지 보장한다.

명령 단계의 검사는 원자성과 즉시 피드백을 위한 사전 검사다. 가능한 topology helper와 오류 코드는 Phase 1에서 추출한 공용 구현을 재사용하고, 명령 성공 뒤 입력 완료 시에는 반드시 `validateOrganizationSnapshot`으로 전체 조직을 다시 판정한다.

완료 게이트:

- 모든 조직 변경은 성공한 새 초안 또는 위치 있는 실패 중 하나다.
- 부모 한 방향에 자식이 둘 이상 저장되지 않는다.
- 한 필드의 수정이 다른 시작값을 바꾸지 않는다.
- 이름 수정이나 회원 배열 순서 변경으로 `memberKey`가 바뀌지 않는다.
- 성공한 모든 편집 명령이 이전 준비 상태와 활성 전달 객체를 해제한다.

### WP4 — 피라미드 조직 시각화

**선행 조건:** WP3 완료  
**파일 범위:** 조직 트리, 회원 선택·추가·이동 UI

작업:

1. `parentMemberKey + sideAtParent`에서 렌더용 자식 인덱스를 파생한다.
2. 루트부터 좌·우 방향을 보존한 피라미드 트리를 그린다.
3. 각 노드에 이름·회원 ID·레벨과 입력 완성 상태를 표시한다.
4. 빈 좌·우 슬롯에 `스스로` 상태와 회원 추가 동작을 제공한다.
5. 자식이 있는 방향은 `CHILD`, 비어 있는 방향은 `SELF`로 파생 표시한다.
6. 노드 선택과 폼 편집이 같은 회원을 가리키게 한다.
7. 깊거나 넓은 조직에서 레이아웃이 겹치지 않도록 스크롤과 최소 크기를 적용한다.

완료 게이트:

- 자식 포인터를 별도 저장하지 않고 같은 초안에서 항상 같은 트리가 나온다.
- 좌·우 위치를 글자와 구조로 모두 식별할 수 있다.
- 마우스 없이 노드 선택, 빈 슬롯 추가, 회원 편집이 가능하다.

### WP5 — 기간·조직 전용 검증과 정규 전달 객체

**선행 조건:** WP3~WP4 완료  
**파일 범위:** Phase 1 검증의 최소 리팩터링, 정규화, 오류 매핑

작업:

1. Phase 1의 기간 검증을 공개 `validatePeriod`, 조직·시작값 검증을 공개 `validateOrganizationSnapshot` 계약으로 추출한다.
2. 기존 `validatePlan`이 추출된 동일 구현을 호출하도록 하여 규칙 복제를 막는다.
3. Draft 필드의 공백, 숫자 문자열, 방향과 부모를 명시적으로 파싱한다.
4. 새 `snapshotId`를 가진 계산용 조직 입력 후보를 만들고 Phase 1 검증을 실행한다. 실패한 시도의 ID는 게시하지 않는다.
5. `ERROR`가 하나라도 있으면 성공 전달 객체를 반환하지 않고, `WARNING`은 보존하되 완료를 차단하지 않는다.
6. 성공하면 `organizationSnapshotId`가 후보의 ID를 참조하는 인메모리 `PlanProject`와 계산용 조직 입력을 함께 게시한다.
7. 오류 코드·심각도·위치·설명·수정 제안을 회원 노드·입력 필드·전체 요약에 연결한다.
8. 가짜 allocations를 만들거나 `calculatePlan`을 호출하지 않는다.

완료 게이트:

- 유효한 초안은 Phase 1 계약과 정확히 같은 필드의 계산용 조직 입력이 된다.
- 잘못된 초안은 부분 전달 객체나 계산 결과를 만들지 않는다.
- 경고만 있는 결과는 경고를 보존한 성공이며, 오류가 있는 결과만 실패다.
- 기존 `validatePlan`의 오류 코드·정렬·Phase 1 테스트 결과가 유지된다.
- 같은 초안 검증이 초안 또는 과거에 만든 전달 객체를 변경하지 않는다.

### WP6 — 입력 완료 흐름과 기본 사용성

**선행 조건:** WP2~WP5 완료  
**파일 범위:** 화면 통합, 오류 경험, 반응형·접근성 스타일

작업:

1. 프로젝트 기간, 조직도, 선택 회원 폼, 오류 요약을 한 흐름으로 조합한다.
2. 입력 중에는 부분 오류를 해당 필드 가까이 보여 주고 전체 검증 시 오류 요약으로 이동한다.
3. `ERROR`가 있으면 `입력 완료`를 차단하고 첫 오류로 이동할 수 있게 한다. `WARNING`은 따로 표시하지만 차단하지 않는다.
4. 성공하면 현재 초안에서 만든 새 설정 전달 객체와 준비 완료 상태를 화면에 표시한다.
5. 완료 뒤 초안을 다시 수정하면 준비 상태와 활성 전달 객체를 즉시 해제한다. 이전 객체 자체는 변하지 않지만 Phase 3 입력으로 계속 사용하지 않는다.
6. 저장되지 않는다는 안내와 새 프로젝트 초기화 경고를 유지한다.
7. 모바일 폭, 확대, 키보드 초점, 오류 색상과 텍스트를 점검한다.

완료 게이트:

- 처음 방문한 사용자가 안내에 따라 유효한 한 루트 조직을 만들 수 있다.
- 필드 오류와 조직 오류의 위치를 화면에서 찾을 수 있다.
- 입력 완료 뒤 Phase 3가 받을 프로젝트·기간·조직 입력을 개발자 도구 없이 검증할 수 있는 요약이 보인다.
- 일일 계획표, 계산 결과, 자동 최적화 버튼이 없다.

### WP7 — 회귀 검증, CI, 개발 로그

**선행 조건:** WP6 완료  
**파일 범위:** 전체 테스트, 설정, CI, 문서, 당일 개발 로그

작업:

1. 9절의 Phase 2 인수 사례를 자동 테스트와 연결한다.
2. `src/domain/**`와 `src/engine/**`의 기존 95% 기준을 디렉터리별로 유지한다.
3. `src/application/**`의 branches·functions·lines·statements를 각각 95% 이상으로 별도 측정한다.
4. `src/ui/**`는 부트스트랩을 제외하고 branches 85%, functions·lines·statements 90% 이상으로 별도 측정하며 핵심 상호작용을 테스트한다.
5. 타입 검사, 전체 테스트, 커버리지 검사, 프로덕션 빌드를 각각 실행한다.
6. 빌드 뒤 `npm run smoke:dist`로 `/ngplan/` 자산 URL과 참조 산출물 존재를 자동 검사한다.
7. `npm run preview`의 `/ngplan/` 주소에서 첫 화면과 핵심 입력 흐름을 수동 브라우저 스모크하고 결과를 기록한다.
8. 실제 변경, 결정 이유, 테스트, 알려진 저장 제한을 한국어 개발 로그에 기록한다.
9. 구현 완료 뒤에만 `ROADMAP.md`의 Phase 2 상태를 변경한다.

완료 게이트:

- Phase 1 전체 회귀 테스트가 그대로 통과한다.
- Phase 1, Application, UI의 디렉터리별 커버리지 기준이 각각 통과하며 전체 평균으로 서로를 가리지 않는다.
- 프로젝트·조직 입력 핵심 사용자 흐름이 DOM 테스트로 통과한다.
- 타입 검사, 전체 테스트, 커버리지 검사, 프로덕션 빌드와 `smoke:dist`가 모두 성공한다.
- 개발 로그가 구현 내용과 제외 범위를 설명한다.

## 8. 입력·검증·정규화 파이프라인

Phase 2의 입력 완료 동작은 다음 순서를 따른다.

| 순서 | 단계 | 입력 | 출력 |
|---:|---|---|---|
| 1 | 사용자 편집 | 폼 문자열, 선택한 회원·슬롯 | 새 `ProjectSetupDraft`, 기존 준비 상태 해제 |
| 2 | 명령 사전 검사 | 현재 초안, 추가·이동·삭제 명령 | 성공한 새 초안 또는 원자적 실패 |
| 3 | 초안 검증 | 기간·회원·시작값의 불완전한 필드 | 필드별 `ERROR/WARNING` |
| 4 | 명시적 파싱 | 오류 없는 문자열 필드 | 기간·회원·시작값 후보 |
| 5 | 후보 생성과 정본 검증 | `PeriodInput` 후보와 새 `snapshotId`가 있는 `OrganizationSnapshotInput` 후보 | Phase 1 기간·조직 `ValidationReport` |
| 6 | 전달 객체 게시 | `ERROR` 없는 후보, `projectId`, 제목·시간대 | `PlanProject + OrganizationSnapshotInput`, 보존된 경고 |
| 7 | 준비 완료 표시 | 성공 전달 객체 | Phase 3 진입 가능 상태와 요약 |

다음 우회 구현은 금지한다.

- `Number('') === 0`을 이용해 빈값을 0으로 처리
- TypeScript `as OrganizationSnapshotInput`으로 검증 건너뛰기
- UI 컴포넌트에 순환·루트·중복 슬롯 규칙 복제
- 부모와 자식 양쪽에 연결을 권위 저장
- Phase 2 준비 상태 확인을 위해 완전한 0 배정표 생성
- 편집 초안과 성공 전달 객체가 같은 변경 가능한 객체를 공유

| 배열 인덱스나 회원 ID를 내부 키로 사용 | 정렬·ID 수정 시 선택과 연결 붕괴 | 주입 가능한 안정 키 생성기 사용 |
| 삭제 한 번으로 서브트리 소실 | 복구할 수 없는 입력 손실 | 비잎 삭제 차단, 명시적 안내 |
| 가짜 0 배정표로 Phase 1 계산 호출 | Phase 2와 Phase 3 검증 경계 혼합 | 조직 전용 검증 API와 파이프라인 계약 고정 |
| 임시 저장을 편의상 추가 | Phase 6 데이터 정책 선점 | 모든 브라우저 저장 금지와 새로고침 제한 안내 |
| 입력 완료 후 수정해도 예전 결과가 활성 상태로 남음 | Phase 3가 낡은 조직을 사용 | 모든 Draft 변경에서 준비 상태와 활성 전달 객체 해제 |
| 피라미드 시각화에만 의존 | 키보드·작은 화면 사용 불가 | 폼 기반 배치 편집, 스크롤, 텍스트 방향 표시 |
| Pages 하위 경로를 무시한 라우팅 | 배포 후 흰 화면 재발 | Phase 2 라우터 미도입, `/ngplan/` 빌드 스모크 |
| Phase 2 UI가 전체 제품 UI로 팽창 | 일정 지연과 Phase 경계 붕괴 | 기능 화면·기본 접근성까지만 완료 기준으로 사용 |

## 12. Phase 2 완료 정의

아래를 모두 만족해야 `ROADMAP.md`의 Phase 2 상태를 완료로 바꿀 수 있다.

- Phase 2 진입 결정이 기술 설계와 개발 로그에 기록되어 있다.
- 새 반월 `PlanProject` 초안을 만들고 기간과 제목을 수정할 수 있다.
- 회원 ID·이름·레벨·부모·좌우 위치와 네 시작값을 입력하고 수정할 수 있다.
- 피라미드 화면이 권위 연결값에서 루트·좌·우·빈 슬롯·`CHILD/SELF`를 파생해 보여 준다.
- 잘못된 숫자와 조직 연결이 위치 있는 오류로 표시되고 입력 완료 전에 차단된다. 경고는 보존되지만 완료를 차단하지 않는다.
- 유효한 초안만 Phase 3가 사용할 `PlanProject + OrganizationSnapshotInput` 전달 객체로 정규화된다.
- 완료 뒤 Draft가 바뀌면 이전 전달 객체가 활성 입력에서 해제되고 재검증을 요구한다.
- 새 프로젝트에 이전 조직이나 시작값이 자동 이월되지 않는다.
- Phase 1 기간·조직 검증은 한 구현에서 재사용되며 기존 계산 결과와 테스트가 유지된다.
- 키보드, 오류 연결, 작은 화면, 초점 표시의 기본 사용성 검증이 통과한다. 정식 접근성·브라우저 감사는 Phase 7에 남아 있다.
- `typecheck`, 전체 테스트, 디렉터리별 커버리지 검사, 프로덕션 빌드와 `smoke:dist`가 성공한다.
- 수동 preview의 `/ngplan/` 경로에서 프로젝트 입력 화면과 최소 상호작용이 정상이다.
- 날짜별 작업표, 자동 최적화, 확정·실제, 영구 저장과 종료 기능이 구현되지 않았다.
- 실제 변경의 한국어 개발 로그가 작성되어 있다.

완료 후 Phase 3는 이 설정 전달 객체를 입력으로 받아 날짜별 수동 계획표와 Phase 1 계산 결과 표시를 구현한다. Phase 2의 Draft 상태나 UI 내부 구조를 계산 엔진에 전달하지 않는다.
