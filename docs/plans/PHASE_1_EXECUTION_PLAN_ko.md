## 1. Phase 1의 목적

조직, 시작값, 날짜별 직접 입력을 받아 다음을 정확하고 재현 가능하게 계산하는 UI 독립 코어를 완성한다.

- 날짜별 하위 조직 실적의 상위 연쇄 합산
- 회원별 일일 PVP 적용, 커미션 단계, 초기화 또는 이월
- 일일 초기화와 별개인 보름 원본 누적
- 레벨별 개인 PVP 목표와 보름 좌·우 2,500 판정
- 전체 반월의 날짜별 감사 결과

Phase 1은 **주어진 입력을 평가하는 계산기**를 만든다. 필요한 신규 PV를 자동으로 찾는 최적화기는 만들지 않는다.

## 2. 성공 조건

Phase 1 완료 시 다음 질문에 코드가 한 가지 답만 내야 한다.

1. 이 입력 집합에 기록된 날짜별 신규 PVP·조직 좌·우는 얼마인가?
2. 전일 잔액을 더하고 PVP를 작은 쪽에 적용하면 어느 커미션 단계인가?
3. 커미션 이후 다음 영업일로 넘어가는 PVP·좌·우는 얼마인가?
4. 일일 초기화와 무관한 보름 원본 누계는 얼마인가?
5. 개인 PVP와 보름 좌·우 목표는 달성되었는가?
6. 어떤 입력과 중간값 때문에 그 결과가 나왔는가?

### WP2 — 도메인 타입과 규칙

**선행 조건:** WP1 완료  
**파일 범위:** `types.ts`, `constants.ts`, `pv.ts`

작업:

1. PV, 회원 키, 날짜, 방향의 혼용을 막는 타입 경계를 만든다.
2. 권위 있는 입력 타입과 파생 결과 타입을 분리한다.
3. OpeningState의 네 값을 별도 필드로 만든다.
4. RuleSet에 공식 단계와 확정된 정책을 모은다.
5. 개별 PV와 모든 파생 덧셈·합계에 같은 안전 정수 검사 함수를 사용하게 한다.
6. 계산 결과에 규칙·엔진 버전과 감사 필드를 포함한다. 계획·실제 리비전은 Phase 5 애플리케이션 계층의 책임으로 남긴다.

완료 게이트:

- 보름 시작 PVP를 일일 PVP 잔액 자리에 실수로 전달하기 어렵다.
- 연결 방향 원본과 `SELF` 직접 입력을 타입과 검증으로 구분할 수 있다.
- 계산 상수가 엔진 구현 안에 중복되지 않는다.
- 안전 범위를 넘은 합계가 반올림되지 않고 식별 가능한 오류가 된다.

### WP3 — 기간과 입력 검증

**선행 조건:** WP2 완료  
**파일 범위:** `period.ts`, `validation.ts`, `domain/__tests__/period.test.ts`, `domain/__tests__/validation.test.ts`

작업:

1. 연·월과 반기에서 ISO 날짜 목록을 생성한다.
2. 윤년과 월말을 외부 현재 시각 없이 계산한다.
3. 확정된 일요일 정책을 적용한다.
4. PV의 0 이상 정수와 안전 범위를 검증한다.
5. 입력뿐 아니라 합산 중간값이 안전한 정수 범위를 넘으면 식별 가능한 오류로 중단하도록 공통 검사 계약을 정한다.
6. 회원 ID, 부모 참조, 슬롯 중복, 순환, 루트·연결 조건을 검증한다.
7. 연결 방향 직접 입력과 반월 밖 날짜를 거부한다.

완료 게이트:

- `CALCULATION_CASES.md`의 Phase 1 달력·검증 확정 사례가 통과한다.
- 오류가 회원·날짜·방향·필드 위치를 가진다.
- 잘못된 입력에서 계산 엔진이 부분 결과를 만들지 않는다.

### WP4 — 날짜별 조직 전파

**선행 조건:** WP3 완료  
**파일 범위:** `organization.ts`, 조직 테스트

작업:

1. 검증된 조직에서 자식 인덱스와 후위 계산 순서를 만든다.
2. 각 회원의 직접 PVP와 `SELF` 값을 읽는다.
3. 자식이 있는 방향에는 자식의 `T`를 사용한다.
4. 각 회원의 `T = P + L + R`을 한 번 계산한다.
5. 시작·이월·정산값이 전파 입력에 들어가지 않게 구조적으로 분리한다.
6. 모든 서브트리 덧셈을 안전 합계 함수로 수행한다.

완료 게이트:

- `CALCULATION_CASES.md`의 Phase 1 조직 전파 확정 사례가 통과한다.
- 회원 입력 순서를 섞어도 결과가 같다.
- 다단계 경로에 추가한 PV가 각 상위의 정확한 한 방향에 한 번씩만 증가한다.

### WP5 — 일일 장부

**선행 조건:** WP4 완료  
**파일 범위:** `daily-ledger.ts`, 일일 테스트

작업:

1. `carryIn + 오늘 원본`을 항목별로 더한다.
2. 작은 쪽과 확정된 동률 정책을 판정한다.
3. PVP를 복사한 판정값에만 전량 적용한다.
4. 가장 높은 공식 단계 하나를 찾는다.
5. 발생 시 세 잔액을 0으로, 미발생 시 원래 세 항목을 그대로 반환한다.
6. 입력 객체가 변하지 않는지 검증한다. 최적화용 초과 소멸 지표는 Q-SIM-02 확정 뒤 Phase 4에서 추가한다.
7. `carryIn + 오늘 원본`과 PVP 판정 덧셈의 범위를 검사한다.

완료 게이트:

- `CALCULATION_CASES.md`의 Phase 1 일일 장부·횟수 확정 사례가 통과한다.
- 모든 공식 단계의 직전·정확한 값·직후가 검증된다.
- PVP가 적용 후 다른 쪽보다 커져도 분할·재적용되지 않는다.
- 미발생 PVP가 좌·우 잔액에 합쳐지지 않는다.

## 8. 계산 파이프라인 계약

Phase 1의 한 번의 전체 계산은 반드시 다음 순서를 따른다.

| 순서 | 단계 | 입력 | 출력 |
|---:|---|---|---|
| 1 | 전체 검증 | 프로젝트·조직·시작값·정규화 직접 입력·규칙 | 오류·경고 또는 정규 입력 |
| 2 | 조직 순서 | 검증된 회원 배치 | 후위 계산 순서·자식 인덱스 |
| 3 | 달력 | 연·월·반기·휴무 정책 | 순서가 있는 날짜 목록 |
| 4 | 날짜 원본 | 날짜 직접 입력·조직 | 전 회원 `P/L/R/T` |
| 5 | 일일 정산 | 회원 `carryIn`·그날 `P/L/R` | `DailySettlement`과 다음 `carryOut` |
| 6 | 보름 누적 | 그날 원본 `P/L/R` | 회원별 누적 원본 |
| 7 | 마감 평가 | 시작값·누적 원본·레벨·규칙 | 개인 PVP·좌·우 목표 상태 |
| 8 | 결과 조립 | 모든 중간·최종 결과 | 버전과 추적값이 있는 불변 결과 |

일일 정산을 먼저 해 원본을 0으로 만든 뒤 보름 누계에 더하는 구현은 금지한다. 조직 전파에 자식의 일일 잔액이나 정산 결과를 넣는 구현도 금지한다.

## 9. 테스트 실행 계획

### 9.1 필수 명령

Phase 1 완료 보고 전에 다음 명령을 각각 실행한다.

1. `npm run typecheck`
2. `npm test -- --run`
3. `npm run test:coverage`
4. `npm run build`

CI와 로컬에서 같은 명령을 사용한다. 감시 모드 성공 화면만으로 테스트 완료를 판단하지 않는다.

### 9.2 테스트 층위

| 층위 | 목적 | 예시 |
|---|---|---|
| 순수 단위 | 하나의 공식·경계 검증 | 공식 단계, PVP 적용, PVP 목표 잔여량 |
| 구조 단위 | 조직과 날짜 구조 검증 | 후위 전파, 순환·중복 슬롯, 월말 |
| 다일 통합 | 이월과 두 장부의 독립성 검증 | DAY-003, DAY-009, DAY-010 |
| 전체 반월 | 달력·조직·일일·보름 조합 검증 | CAL 계열과 다단계 조직 |
| 불변성 | 결과 성질 검증 | 입력 비변경, 결정성, 0 이상 정수 |

### 9.3 필수 경계

- 모든 단계 `n`에 대해 가능한 곳에서 `n-1`, `n`, `n+1`
- 59,999와 60,000, 60,000 초과
- PVP 0, 좌 또는 우 0, 매우 불균형한 좌·우
- PVP 적용 후 방향 역전
- 좌·우 동률
- 시작 잔액만 있는 날, 신규 원본만 있는 날, 둘 다 있는 날
- 커미션 발생 다음 날과 미발생 다음 날
- 상반기·하반기, 28·29·30·31일 월말
- 일요일이 기간 시작·중간·마지막에 있는 경우
- 잎·한쪽 가지·양쪽 가지·세 단계 이상 조직
- 음수·소수·중복·순환·반월 밖 날짜·연결 방향 입력

## 10. 검토 체크포인트

### 체크포인트 A — 데이터 모델

- 전파 원천이 그 날짜 신규 원본뿐인가?
- 서브트리 값이 상위 경로마다 정확히 한 번 반영되는가?
- 자식 커미션 결과가 부모 원본을 바꾸지 않는가?

- PVP 적용이 원본을 바꾸지 않는가?

- 시작 좌·우 잔액이 보름 2,500을 줄이지 않는가?

### 체크포인트 D — 공개 결과

- 사용자가 화면에서 요구한 모든 중간 결과를 만들 수 있는가?
- 오류가 어느 회원·날짜·방향에서 났는지 알 수 있는가?
- 규칙 버전과 보존된 전체 입력 스냅샷으로 결과를 재현할 수 있는가? 입력 fingerprint는 Phase 6 무결성 기능이며 Phase 1 재현 수단이 아니다.

## 12. Phase 1 완료 정의

아래를 모두 만족해야 `ROADMAP.md`의 Phase 1 상태를 완료로 바꿀 수 있다.

- 차단 질문의 답이 설계와 계산 사례에 반영되어 있다.

- Phase 1 대상 확정 계산 사례가 모두 자동화되어 통과한다.
