# ngplan Phase 6A 실행 계획 — 클라우드 안전 저장

> 기준일: 2026-07-19
> 구현 완료일: 2026-07-26
> 상태: 핵심 구현·운영 DB·Auth 설정 완료, 인증된 브라우저 검수·코드 배포 대기
> 선행 상태: Phase 4 자동 계획은 베타 동결. Phase 4 알고리즘은 이 Phase에서 수정하지 않는다.

## 1. 목표

Phase 4의 자동 계획 알고리즘을 변경하지 않고, 현재 브라우저에만 남는 작업 자료를 기존 Supabase 프로젝트에 안전하게 저장한다.

핵심 목표는 다음 세 가지다.

1. 엄마가 저장 방식이나 충돌을 판단하지 않아도 입력이 자동으로 보존된다.
2. 인터넷이 잠시 끊겨도 IndexedDB에 작업본을 남기고 복구 후 자동으로 원격 저장한다.
3. 계획별 하루 보관본과 숨김/복원 기능으로 과거 자료를 나중에 분석할 수 있다.

## 2. 확정 결정

| 항목 | 결정 |
|---|---|
| Supabase 프로젝트 | 기존 엄마용 Supabase 프로젝트와 기존 로그인·인증 설정을 재사용한다. |
| 허용 사용자 | 기존 허용 계정 두 개만 사용한다. 공개 회원가입은 끈 상태를 유지한다. |
| 업무 시간대 | `America/Sao_Paulo`를 계획의 고정 business timezone으로 사용한다. 기기 위치·브라우저 시간대에 따라 바뀌지 않는다. |
| 타임스탬프 | 저장 시각은 UTC로 기록하고, 계획 날짜와 하루 보관 날짜는 계획의 `America/Sao_Paulo` 기준으로 계산한다. |
| 최신 작업본 | 계획 전체를 하나의 논리적 작업본으로 저장하고 최신 상태가 이전 상태를 덮어쓴다. 셀별 영구 이력은 저장하지 않는다. |
| 자동 저장 | 입력 후 짧은 지연을 둔 IndexedDB 저장과 입력이 멈춘 뒤 원격 저장을 사용한다. 기본값은 로컬 약 0.5초, 원격 약 2초다. 포커스를 잃거나 화면을 떠날 때는 즉시 저장을 시도한다. |
| 저장 충돌 | 사용자에게 선택 화면을 보여주지 않는다. 마지막으로 도착한 전체 작업본이 원격본을 덮어쓴다. 오프라인 중 입력한 작업본은 연결 복구 후 자동 업로드한다. |
| 저장 상태 | `저장 중`, `저장됨`, `오프라인 저장됨`, `저장 실패`를 화면에 표시하고 자동 재시도와 `다시 저장`을 제공한다. |
| 하루 보관본 | 계획·상파울루 날짜별 한 개를 둔다. 그날 저장이 성공할 때마다 최신 상태로 갱신하고, 날짜가 지나면 이전 날짜 보관본은 더 이상 수정하지 않는다. |
| 특별 스냅샷 | 별도 특별 스냅샷은 만들지 않는다. 사용자 화면과 문서에서는 `하루 보관본`이라는 표현을 사용한다. |
| 숨김/복원 | 계획 목록에서 숨기고 다시 보이게 하는 기능만 제공한다. 숨김은 삭제나 잠금이 아니다. |
| 종료 상태 | Phase 6A에서는 `CLOSED` 상태, 종료 잠금, 읽기 전용 전환을 구현하지 않는다. |
| 기존 자료 | 기존 `localStorage` 자료를 이전하지 않는다. Supabase 기반에서 새 작업공간으로 시작한다. |
| 외부 백업 | 여러 앱이 함께 사용하는 Supabase 프로젝트의 외부 백업 정책은 이 Phase에서 다루지 않는다. |
| 요금제 | Supabase Free 플랜 기준으로 설계한다. Supabase 플랫폼 자동 백업이나 PITR을 전제로 하지 않는다. |

## 3. 날짜와 위치의 원칙

Supabase 데이터베이스가 브라질 리전에 있다는 사실과 업무 날짜의 기준은 별개다. 계획은 엄마가 실제 업무를 수행하는 브라질 날짜에 맞춰 `America/Sao_Paulo`로 고정한다.

J님이나 엄마가 한국과 브라질을 오가더라도 같은 계획의 날짜가 기기 위치에 따라 바뀌지 않아야 한다. 따라서 다음 값을 프로젝트에 저장한다.

- `timezone: America/Sao_Paulo`
- `created_at`, `updated_at`, `last_saved_at`: UTC timestamp
- `business_date`: 계획 시간대에서 파생한 ISO date-only 값

기존 계산 코어의 ISO date-only·host timezone 독립 원칙은 유지한다. 이번 변경은 계획의 기준 시간대를 서울에서 상파울루로 명시하는 것이다.

## 4. 저장 구조의 논리 모델

구현 테이블은 `public.ngplan_projects`와 `public.ngplan_daily_backups`다. 기존 공용 `public.workspaces`·`public.workspace_members`의 별도 `ngplan` 작업공간을 사용하며, 애플리케이션은 다음 논리 기능만 저장 포트로 본다.

### 4.0 구현 계약

- 원격 최신 작업본의 문서 형식은 `CloudPlanDocumentV1`이며, `version`, 프로젝트 설정 초안, 수동 계획 초안만 저장한다.
- 현재 화면, 조직도 확대 비율, 자동 계획 체크포인트는 같은 기기에서 작업을 이어가기 위한 IndexedDB 사본에만 저장한다. 다른 기기에서는 원격 원본으로 안전하게 다시 구성한다.
- 한 기기 안의 원격 저장 요청은 항상 한 번에 하나씩 보낸다. 저장 도중 새 입력이 생기면 진행 중 요청이 끝난 뒤 가장 최신 작업본을 다시 저장하여, 같은 기기의 오래된 요청이 나중 입력을 최종적으로 덮지 않게 한다.
- 서로 다른 기기 사이에는 합의한 대로 서버에 마지막으로 도착한 전체 작업본이 우선한다. 사용자에게 충돌 선택 화면을 표시하지 않는다.
- 현재 작업본 갱신과 해당 상파울루 날짜의 하루 보관본 갱신은 하나의 데이터베이스 트랜잭션에서 처리한다.
- 하루 보관본은 Phase 6A에서 데이터베이스에 저장하고 검증하되, 엄마용 복원 선택 화면은 만들지 않는다. 계획 목록에는 최신 작업본과 숨김/복원만 노출한다.
- 공개 스키마 테이블은 명시적 권한 부여와 RLS를 함께 사용하며, 브라우저 역할에는 `DELETE` 권한과 정책을 모두 주지 않는다.

### 4.1 프로젝트 목록과 현재 작업본

- 프로젝트 기본 정보와 `workspace` 식별자를 저장한다.
- 계획 전체의 최신 작업본을 한 개 저장한다.
- 최신 작업본에는 현재 설정, 수동 계획, 화면에 필요한 저장 원본, schema version, revision number, UTC 저장 시각을 포함한다.
- 계산 결과로 다시 만들 수 있는 파생값은 필요 이상으로 영구 저장하지 않는다.

### 4.2 하루 보관본

- 키는 `workspace + project + business_date`다.
- 같은 날짜의 저장은 해당 행의 전체 계획 내용을 갱신한다.
- 다음 날짜가 시작되면 전날 행은 보존하고 새 날짜 행을 만든다.
- 보관본은 향후 데이터 분석과 최근 작업 복구를 위한 자료이며, 사용자에게 사진이나 별도 버전 관리로 설명하지 않는다.

### 4.3 숨김/복원

- 프로젝트에 `hidden` 또는 동등한 보관 표시를 둔다.
- 기본 목록에서는 숨김 프로젝트를 제외한다.
- `숨긴 계획 보기`에서 숨김 계획을 확인하고 복원한다.
- 숨김과 복원은 최신 작업본과 하루 보관본을 삭제하거나 변경하지 않는다.
- 앱에는 영구 삭제 명령을 만들지 않는다.

## 5. 인증과 Supabase 보안 경계

- 기존 Supabase Auth 계정과 로그인 흐름을 재사용한다.
- 브라우저에는 publishable/기존 anon 호환 키만 사용한다.
- `service_role` 또는 새 secret key를 브라우저에 넣지 않는다.
- 공개 스키마에 노출되는 모든 저장 테이블은 RLS를 활성화한다.
- 두 허용 계정이 같은 작업공간 자료를 읽고 쓰도록 명시적인 workspace 접근 정책을 둔다.
- `user_metadata`를 권한 판단에 사용하지 않는다. 필요할 경우 서버 관리용 `app_metadata` 또는 별도 접근 목록을 사용한다.
- DELETE 권한과 DELETE 정책은 클라이언트 역할에 제공하지 않는다.
- UPDATE 정책에는 SELECT 정책과 `USING`·`WITH CHECK`를 함께 둔다.

## 6. 오프라인 저장과 자동 덮어쓰기

IndexedDB는 원본이 아니라 다음 복구 정보를 가진 로컬 사본이다.

- 마지막으로 성공한 원격 작업본
- 아직 원격에 도착하지 않은 최신 로컬 작업본
- 마지막 시도 시각과 저장 상태
- schema version과 workspace/project 식별자

입력 중에는 로컬 작업본을 먼저 저장한다. 원격 저장이 실패하면 자동 재시도하고, 브라우저가 다시 연결되면 가장 최신 로컬 작업본 전체를 원격에 업로드한다. 이때 원격의 중간 변경 여부를 사용자에게 묻지 않고 마지막 도착 작업본으로 덮어쓴다.

이 단순한 정책은 실시간 공동 편집을 제공하지 않는다는 현재 운영 조건에 맞춘 것이다. 데이터가 사라지는 것을 막기 위해 하루 보관본을 별도로 남기며, 저장 실패 상태는 화면에 분명히 표시한다.

## 8. 구현 결과

1. `supabase/migrations/20260725212656_phase_6a_cloud_safe_storage.sql`에 현재 작업본, 하루 보관본, 저장 리비전·시각·작성자 trigger, RLS와 명시적 권한을 구현했다.
2. `supabase/migrations/20260725212904_phase_6a_advisor_cleanup.sql`에 복합 외래 키 인덱스와 기존 공용 정책과 겹치는 ngplan 보조 정책 정리를 구현했다.
3. 두 기존 Auth 사용자를 별도 `ngplan` 작업공간 구성원으로 등록했다. 앱에는 가입 UI가 없고 브라우저에는 publishable key만 전달한다. 로컬/CI와 실제 공유 Supabase Auth 모두 신규 가입 차단 상태다.
4. `src/cloud/`에 버전이 있는 전체 계획 문서, Supabase 저장소, IndexedDB 사본, 로컬 0.5초·원격 2초 저장 조정기와 재시도 정책을 구현했다.
5. `src/ui/CloudApp.tsx`에 Google 로그인, 계획 목록, 새 계획, 숨김/복원, 저장 상태와 수동 재시도를 연결했다.
6. 프로덕션 진입점은 기존 `localStorage` 복원 경로를 사용하지 않고 클라우드 작업공간에서 새로 시작한다. 기존 로컬 저장 코드는 하위 UI 단위 테스트와 과거 호환 경계에만 남는다.
7. GitHub Pages 빌드에는 Supabase 공개 환경 변수를 주입하고, CI에는 격리된 Supabase DB 테스트 단계를 추가했다.
8. 최신 Supabase 공식 문서와 changelog를 확인한 뒤 운영 DB에 두 migration을 적용했다. RLS·권한·같은 날 보관본 갱신·날짜 경계·숨김/복원을 rollback SQL로 검증하고 advisor를 다시 확인했다.

## 9. 완료 기준

- 엄마가 로그인 후 저장 방식을 선택하지 않고 계획을 편집할 수 있다.
- 입력 후 저장 상태가 화면에 나타난다.
- 인터넷이 끊겨도 최신 입력이 IndexedDB에 남는다.
- 연결 복구 후 로컬 최신 작업본이 자동으로 원격에 저장된다.
- 같은 계획의 최신 상태는 한 개의 논리 작업본으로 복원된다.
- 상파울루 날짜 기준으로 하루 보관본이 생성·갱신·고정된다.
- 한국에서 접속해도 계획 날짜가 한국 날짜로 바뀌지 않는다.
- 숨긴 계획은 기본 목록에서 사라지고 복원할 수 있다.
- 앱에서 영구 삭제가 불가능하다.
- 두 허용 계정만 같은 workspace 자료를 읽고 쓸 수 있다.
- 익명·미허용 계정은 실제 계획 자료를 읽을 수 없다.
- RLS·저장 실패·오프라인·손상 데이터 테스트가 통과한다.
- Phase 4 계산 테스트와 기존 수동 계획 테스트가 그대로 통과한다.

### 9.1 현재 검증 상태

- 타입 검사, 53개 테스트 파일의 632개 테스트와 전체 커버리지 기준이 통과했다.
- `cloud` 모듈은 statement 94.33%, branch 86.41%, function 90.66%, line 95.95%를 충족했다.
- 프로덕션 빌드, `dist` 경로·worker 스모크 검사와 npm 보안 감사가 통과했다.
- 실제 로그인 전 화면을 데스크톱·375px 모바일 폭에서 확인했고 브라우저 오류가 없음을 확인했다.
- 운영 DB의 두 계정 접근, 익명 차단, 클라이언트 DELETE 차단, 저장 리비전, 숨김/복원과 상파울루 날짜 하루 보관본을 rollback 검증했다.

### 9.2 배포 전 남은 운영 검수

- 기존 허용 Google 계정으로 실제 OAuth 왕복과 GitHub Pages 배포 주소의 redirect 허용 여부를 확인한다.
- 실제 공유 Supabase Auth는 2026-07-26 Dashboard에서 신규 가입을 차단했고, 공개 설정의 `disable_signup=true`와 Google provider 활성 상태를 다시 확인했다. 기존 두 Auth 사용자는 계속 로그인할 수 있다.
- 기존 Site URL과 다른 앱의 Redirect URL은 변경하지 않고, 운영 Redirect URL `https://mworkroom.github.io/ngplan/`만 허용 목록에 추가했다.
- 인증된 실제 브라우저에서 새 계획 생성·편집·새로고침·숨김/복원을 한 번 검수한다.
- 브라우저 네트워크 차단·복구로 `오프라인 저장됨`에서 원격 `저장됨`으로 자동 전환되는지 운영 화면에서 확인한다.
- 현재 변경은 아직 Git commit·push·GitHub Pages 배포를 하지 않았다.
