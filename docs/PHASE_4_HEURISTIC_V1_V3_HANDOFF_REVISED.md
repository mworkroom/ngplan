## 1. 이 문서의 목적과 권위 범위

이 문서는 2026년 8월에 진행한 V1~V3 자동 계획 실험을 나중에 다시 이어가기 위한 단일 인수인계 문서다. 다음 내용을 대화 기록에서 다시 복원하지 않아도 되게 하는 것이 목적이다.

- V1, V2, V3가 각각 어떤 코드 버전인지
- 엄마 수동안과 자동안이 실제로 어떻게 달랐는지
- 어떤 설명을 잘못 해석했고, 어떤 규칙이 뒤늦게 확정됐는지
- 점수 조정과 후보 생성 실험이 왜 반복해서 흔들렸는지
- 현재 무엇이 해결됐고 무엇이 해결되지 않았는지
- Phase 4를 다시 열기 전에 어떤 증거와 도구가 먼저 필요한지
- 새 후보 생성기를 어떤 순서로 검증해야 하는지

이 문서는 시행착오와 재개 맥락을 보존하는 인수인계 문서다. 비즈니스 규칙과 정확한 계산 계약은 **V3를 보존한 동일한 freeze commit** 안의 다음 자료를 따른다.

1. [통합 요구사항](./requirements/pyramid-app-requirements-v2.md)
2. [계산 사례](./CALCULATION_CASES.md)
3. [기술 설계](./TECHNICAL_DESIGN.md)
4. [Phase 4 실행 계획](./plans/PHASE_4_EXECUTION_PLAN_REVISED.md)
5. `src/optimizer/__tests__/202608a-gold-regression.test.ts`
6. V3 목적함수와 후보 생성기의 단위 테스트

이 자료들이 서로 충돌하면 어느 하나를 임의로 선택하지 않는다. 충돌을 먼저 기록하고, 요구사항·계산 사례·기술 설계·실행 계획·코드·회귀 테스트를 함께 일치시킨 뒤 작업을 재개한다. 오래된 테스트가 존재한다는 이유만으로 그 테스트를 현재 비즈니스 규칙보다 우선하지 않으며, 반대로 대화 요약만 보고 기존 계산 계약을 조용히 바꾸지도 않는다.

이 문서는 V3 코드·테스트·정본 문서와 같은 freeze branch 및 tag에 보존한다. `main`의 V2와 공개 배포 상태를 이 문서의 V3로 오인하지 않는다.

### 2.3 나중에 가장 먼저 확인할 것

1. `git status --short`로 freeze checkout에 미커밋 변경이 없는지 확인한다.
2. `git branch --show-current`와 `git rev-parse HEAD`로 현재 branch와 commit을 확인한다.
3. `src/optimizer/constants.ts`의 policy/objective/checkpoint/worker protocol 버전을 확인한다.
4. freeze branch와 tag가 원격에 있는지 확인하고, tag가 가리키는 commit을 Git에서 조회한다.
5. 공개 앱이 어느 commit을 제공하는지는 배포 자산을 별도로 확인한다. freeze branch push는 `main` 배포가 아니므로 V3 배포 증거가 아니다.

## 3. 정답지와 입력 조건

### 3.1 정답지의 의미

엄마가 약 15시간 동안 직접 숫자를 옮겨 완성하고 만족한다고 확인한 `202608A 민경욱 사용중` 계획이 처음으로 확보된 승인 수동안이다. 이것은 날짜별 셀을 그대로 복제해야 하는 절대 최적해 증명은 아니다. 현재 규칙으로 다시 계산했을 때 자동안보다 좋은지 판별하는 gold 비교 자료다.

이 문서에서 **승인 수동안**은 다음 조건을 충족한 계획을 뜻한다.

1. 엄마가 더 수정할 곳이 없다고 명시적으로 확인했다.
2. 해당 시점의 조직과 회원별 시작값을 다시 확인했다.
3. 자동 계산 직전의 입력과 엄마 수정 완료본을 서로 구분해 보존했다.
4. 동일 평가기로 다시 계산할 수 있는 불변 export 또는 sanitized fixture가 있다.
5. 승인일과 승인 상태가 기록되어 있다.

저장소에는 실제 계정·프로젝트·회원 UUID를 제거한 다음 자료가 있다.

- `src/optimizer/__tests__/202608a-regression-fixture.ts`

- `AUGUST_2026_FIRST_HALF_GOLD_BUNDLE`: 베로니카 좌 시작값 0인 역사 비교 조건

작업 중 다음 이름들이 등장했다.

앞으로 gold 1건마다 다음 자료를 한 묶음으로 보존한다.

`mworkroom/ngplan`은 공개 저장소다. 현재 fixture는 계정·프로젝트·회원 UUID를 제거했지만 표시 이름까지 완전한 익명 alias로 바꾸지는 않았다. 같은 이름들은 V2의 `origin/main` 문서와 fixture에도 이미 존재하므로 이번 freeze branch가 처음 공개하는 값은 아니다.

## 4. 용어와 규칙을 바로잡은 과정

### 4.1 수당 “N번”

엄마가 말한 수당 횟수는 수당 발생일 수가 아니라 단계별 환산 횟수다.

| 수당 단계 | 환산 횟수 |
| ---: | ---: |
| 300 | 1회 |
| 700 | 2회 |
| 1,500 | 4회 |
| 2,400 | 8회 |

예를 들어 700단계를 4일 받으면 발생일은 4일이고 환산은 8회다. 과거에 “13회”를 13영업일 모두 수당 발생으로 해석한 접근은 잘못이었다.

### 4.2 기본 몫은 PVP 목표나 조직 깊이가 정하지 않는다

엄마는 높은 수당을 맞추기 어려운 회원이 실제 조직에서 2레벨에 많은 탓에 한동안 “2레벨을 우선해야 한다”고 설명했다. 이것을 코드가 문자 그대로 PVP 목표 집단·조직 깊이 우선순위로 받아들인 것이 V1/V2 평가의 핵심 오해였다.

최종 확인된 규칙은 다음과 같다.

- 비루트 회원의 좌·우 보름 목표가 1,500이면 기본 몫은 환산 5회다.
- 좌·우 보름 목표가 2,500이면 기본 몫은 환산 8회다.
- PVP 목표 700·1,500·2,400, 이름의 마커, 조직 깊이는 기본 몫을 만들지 않는다.
- 아래 회원의 기본 몫과 비루트 전체 환산 합계는 맨 위 회원의 추가 수당보다 우선한다.
- 기본 몫을 모두 지킨 뒤에만 추가 기회의 공평성과 맨 위 회원 결과를 비교한다.

회원별 기본 몫 부족량의 개념식은 다음과 같다.

```text
기본 몫 목표(member) =
  fortnightSideTarget == 1,500 ? 5
  : fortnightSideTarget == 2,500 ? 8
  : 계약 오류

기본 몫 부족량(member) =
  MAX(0, 기본 몫 목표(member) - 실제 수당 환산 횟수(member))
```

V3의 실제 objective field와 계산 계약은 다음과 같다.

- 기본 몫 벡터 field는 `nonRootBaseEntitlementDescendingEquivalentUnitShortfallVector`다.
- 구조상 추가 기회 벡터 field는 `nonRootStructuralOpportunityDescendingEquivalentUnitShortfallVector`다.
- 루트를 제외한 모든 회원을 포함한다. 구현은 화면 통계를 위해 PVP 1,500·2,400 배열과 PVP 700 배열을 따로 만들지만, objective에서는 두 배열을 다시 합치므로 PVP 목표 집단이 우선순위에 영향을 주지 않는다.
- 기본 몫 벡터는 각 비루트 회원의 `MAX(0, 기본 몫 목표 - 실제 환산)`을 값 기준 내림차순으로 정렬한다. canonical 회원 순서 벡터가 아니다.
- 구조상 추가 기회 벡터는 각 비루트 회원의 `MAX(0, 구조상 환산 상한 - 실제 환산)`을 값 기준 내림차순으로 정렬한다.
- 두 벡터 모두 앞에서부터 사전식으로 최소화한다. 예를 들어 `[1,1]`은 `[2,0]`보다 우선한다.
- 비루트 전체 환산 합계 `nonRootCommissionEquivalentUnits`는 기본 몫 벡터 다음에 최대화한다.
- 루트는 두 벡터와 비루트 합계에서 제외하고 `rootCommissionGoalShortfallDays`로 별도 비교한다.

구조상 환산 상한은 `deriveMemberCommissionCapacities()`가 계산한다. 회원별 최소 좌·우 raw PV를 하위부터 합산하고, 시작 좌·우 carry와 필요한 PVP를 더해 다음 matched-PV 상한을 만든다.

```text
matched PV 상한 = MIN(
  FLOOR((left + right + pvp) / 2),
  left + pvp,
  right + pvp,
  left + right
)
```

그 PV와 영업일 수 안에서 하루별 `0·300·700·1,500·2,400` 선택으로 얻을 수 있는 최대 환산을 동적 계획법으로 계산한다. 정확한 구현은 `src/optimizer/member-commission-capacity.ts`, comparator는 `src/optimizer/objective.ts`를 따른다.

목적 순서와 충돌 회귀는 `src/optimizer/__tests__/objective.test.ts`의 다음 테스트에 고정되어 있다.

- `keeps every non-root basic entitlement ahead of root gain, payout, and total PV`
- `maximizes confirmed payout and protects structural fairness before discarded excess`
- `balances remaining structural opportunity without using PVP target groups`

이 문서의 자연어만 보고 objective를 다시 작성하지 않는다. 같은 freeze tag의 field·함수·pairwise test를 함께 읽는다.

### 4.3 그 밖의 유지 계약

- 현재 규칙에서는 당일 PVP를 좌·우 중 작은 쪽에 합산한다.
- 누적 PVP 2,400은 영구 달성이며 자동 계획은 그 회원에게 신규 PVP를 배정하지 않는다.
- 자동 직접 입력은 0 또는 30 이상이다.
- 구조상 최소 신규 PV를 `M`이라 할 때 자동 후보는 `M+30`을 넘을 수 없다.
- 100의 배수는 높은 목적이 모두 같은 경우의 가독성 선호일 뿐이다.
- 이름·날짜·정답지 셀을 production 후보에 하드코딩하지 않는다.
- 모든 후보는 같은 Phase 1 평가기로 다시 계산하고 검증한다.
- 후보 생성 실패는 불가능 증명이 아니다.
- 검증된 좋은 후보는 수학적으로 증명된 최적해와 구분한다.

## 5. V1 — 수당 총액에 처음 근접한 버전

### 5.1 무엇을 시도했나

Policy 8은 혼합 1,500/2,500 목표를 계산할 수 있었지만 승인 수동안과 비교하면 수당이 5,640,000원이었다. V1은 점수만 바꾸지 않고 다음 후보 생성기를 추가했다.

- 회원의 좌·우 하위 가지를 같은 날짜 profile로 회전·이동
- 다음 300·700·1,500·2,400 경계까지의 부족량 계산
- 다른 날짜의 현재 단계를 해치지 않는 조직 단위 이동
- 본인 `SELF`와 PVP의 같은 총구매량 안 교환
- 전역 점수가 잠시 나빠지는 후보도 bounded beam에 남기는 local-valley 통과

당시 목적 순서는 맨 위 회원 목표 미달, 확인 수당, 총 신규 PV를 가장 먼저 보았다.

## 6. V2 — 완성형 경계 이동을 넣었지만 운영 평가는 퇴보

### 6.1 무엇을 시도했나

엄마가 표시한 김정미·민경욱·Kelly 사례에서, 경계까지 300이 필요한데 기존 후보가 100 또는 200만 옮긴 미완성 상태로 끝나는 문제가 보였다. V2는 서로 다른 하위 칸의 `200+100`을 모아 경계를 완성하는 결정적 후보를 추가했다.

- 부족량 전체를 채우지 못한 이동은 후보에서 제외
- 큰 여유, 작은 칸, 100에 가까운 칸, 날짜 순서 등 여러 결정적 순회
- 총수당과 총구매량이 같을 때 당시 정의한 PVP 고목표 집단 공평성을 소멸량보다 먼저 비교
- policy `10.0.0`, objective `9.0.0`으로 저장 후보 무효화

### 6.2 재현 가능한 V2 fixture 결과

- 총 신규 PV 23,500
- 확인 수당 6,060,000원
- 소멸 초과 32,756
- 비루트 환산 합계 77회
- 회원별 환산은 V1 fixture와 동일한 `10, 5, 7, 5, 18, 8, 8, 8, 8`

### 6.3 엄마가 실제 V2 화면에서 지적한 문제

엄마는 `202608A 민경욱 · 알고리즘 수정 V2`를 보고 초창기로 돌아간 느낌이라고 평가했다.

- 베로니카는 기본 8회보다 많은 10회를 받고 김정미·박진숙은 기본 몫이 부족해 보였다.
- 맨 위 민경욱은 24회까지 받아 아래 회원의 수당을 가져간 것처럼 보였다.
- Kelly는 이전 사본의 20회와 달리 V2 화면에서 16회였다고 말했다.
- 첫날 시작 잔액으로 300/700 경계만 채우면 되는데 양쪽 실적을 과하게 넣어 베로니카가 300:957처럼 됐다.
- Kelly에게 900이 반복되어 700을 넘는 200씩이 다음 300 기회로 분해되지 못했다.

이 화면 숫자는 고정 V2 fixture와 일치하지 않는다. 사본·시작값·엄마 수정 시점이 섞였기 때문에 정확한 코드 결과로 단정하지 않는다. 그러나 “총수당과 총구매량이 좋아도 기본 몫을 빼앗거나 900을 반복하면 나쁜 계획”이라는 운영 판단은 명확했다.

### 6.4 V2의 근본적인 잘못

V2는 “2레벨 또는 PVP 목표가 높은 회원을 우선한다”는 설명을 실제 목적함수 집단으로 구현했다. 엄마가 뜻한 것은 특정 레벨 특혜가 아니라 좌·우 목표에 따른 기본 몫과, 기본 몫을 지킨 뒤 700 경계를 더 많이 만드는 일이었다.

후보 폭을 5개에서 12개로 늘리는 실험도 실패했다. 총수당은 같았지만 Kelly 22회 대신 남승우 5회·김길주 7회처럼 다른 회원의 몫이 무너졌다. 탐색 폭만 늘리면 좋은 계획이 생기는 것이 아니라 잘못된 목적을 더 넓게 최적화할 뿐이었다.

## 7. V3 — 기본 몫을 올바르게 평가하고 후보 생성 한계를 드러낸 버전

### 7.1 무엇을 바꿨나

V3는 좌·우 목표 1,500→5회, 2,500→8회를 비루트 회원의 기본 몫으로 고정했다. 개념상 목적 순서는 다음과 같다.

1. 비루트 기본 몫 미달 벡터 최소화
2. 비루트 전체 환산 합계 최대화
3. 맨 위 회원 목표 미달 최소화
4. 확인 수당 최대화
5. 비루트 구조상 추가 기회 미달 벡터 최소화
6. 총 신규 PV 최소화
7. 소멸 초과 및 기존 후순위 목적

PVP 목표 집단·이름·조직 깊이 우선순위는 제거했다. 루트 경계 후보도 탐색하되, 이동 좌표가 영향을 주는 회원과 조상 경로의 기존 수당 단계를 보호하도록 바꿨다. checkpoint와 worker protocol을 `5.0.0`으로 올려 V2 저장 후보가 V3처럼 복원되지 않게 했다.

Section 4.2의 field·내림차순 정렬·사전식 비교 계약과 같은 freeze tag의 pairwise test를 함께 읽는다. 이 문서의 목적 순서만 보고 objective를 새로 작성하지 않는다.

따라서 `900 → 700 + 다음 300`은 방향을 설명하는 좋은 예이지만 Kelly 한 명만 보는 production 이동으로 넣으면 안 된다. 승인 수동안 79회를 찾으려면 여러 회원·여러 날짜를 동시에 다시 짜는 더 큰 이웃 탐색이 필요하다.

### 7.5 98개·1,289개 실험의 증거 수준

98과 1,289라는 정확한 개수는 작성 당시의 diagnostic 계측값이며 제품 계약이 아니다.

- 1단계의 **질적 결론**은 `src/optimizer/__tests__/202608a-gold-regression.test.ts`의 `measures the corrected Veronica left opening without replacing the historical fixture`가 자동 재현한다. Kelly 19회 후보가 존재하지만 모두 다른 기본 몫을 훼손하고, 어느 검증 후보도 비루트 78회 또는 현재 V3 objective를 개선하지 못해야 한다.
- 같은 테스트는 원시 후보 수가 정확히 98개라고 assert하지 않는다. 98은 당시 생성기·예산에서 관측한 역사 기록이다.
- 1,289개 2단계 repair 탐색은 임시 계측 코드를 제거했으므로 자동 재현되지 않는다. “당시 제한된 후속 탐색도 개선을 찾지 못했다”는 역사 근거로만 사용한다.

향후 후보 개수를 회귀값으로 고정하려면 fixture, request fingerprint, seed, 후보 budget, 실행 경로와 명령을 함께 보존한다.

## 8. 왜 이 문제가 계속 답이 안 나왔나

### 8.1 엄마의 목표는 비교적 안정적이지만 설명 단위가 상황마다 달랐다

엄마가 추구한 큰 원칙은 일관됐다. 불필요한 구매와 소멸을 줄이고, 각 회원의 기본 몫을 먼저 챙기며, 남는 실적으로 700 경계를 최대한 만든다. 다만 어떤 때는 이를 “2레벨”, “Kelly 우선”, “첫날”, “900을 쪼갠다”처럼 현재 보고 있는 사례의 언어로 설명했다. 그 표현을 일반 규칙으로 곧바로 코딩하면서 의미가 바뀌었다.

### 8.2 사람은 여러 칸을 오가며 임시 악화를 허용하지만 기존 후보는 국소적이었다

엄마는 한 회원의 한 날짜만 고치지 않는다. 하위 좌·우 가지, 본인 PVP, 다음 날짜, 조상과 형제의 수당을 함께 보며 숫자를 넣었다 뺐다 한다. 중간에는 결과가 나빠져도 마지막에 여러 사람을 다시 맞춘다. 단일 이동 또는 짧은 beam은 이 경로를 쉽게 잃는다.

### 8.3 좋은 평가기만으로는 좋은 계획을 선택할 수 없다

V3 comparator는 승인 수동안을 V3보다 좋다고 정확히 판정한다. 그러나 후보 생성기가 승인 수동안과 같은 조직 재배열을 만들지 못하므로 선택할 수 없다. 현재 가장 큰 병목은 평가와 캐시가 아니라 후보 생성이다.

### 8.4 시트 사본과 입력 조건이 비교를 오염시켰다

같은 이름의 사본이 여러 개 생겼고 시작값 0이 나중에 235로 바뀌었다. 화면에서 보고한 V1/V2 회원별 횟수와 코드 fixture가 다른 이유를 하나로 확정할 수 없다. 앞으로는 시트 이름이 아니라 불변 입력 snapshot과 fingerprint를 함께 남겨야 한다.

### 8.5 브라우저 안 제한 시간과 CPU 예산이 있다

후보를 무작정 늘리면 실행 시간이 급격히 증가한다. 57명 조직의 초기 profile을 전부 펼친 실험은 7분 이상 끝나지 않았고, V3의 더 넓은 반복 탐색도 약 90초를 사용하면서 Kelly 19회를 회복하지 못했다. 자동 계산이 J님 컴퓨터에서 약 30초, 엄마 컴퓨터에서 약 60초였던 것도 브라우저가 각 컴퓨터 CPU로 계산하기 때문이다.

### 8.6 승인 수동안이 한 건뿐이라 일반 규칙과 사례 맞춤 규칙을 구별하기 어렵다

현재 gold는 사실상 `202608A` 한 건이다. 한 계획에만 맞는 이동을 추가하면 회귀 수치는 좋아질 수 있지만, 다른 조직에서는 회원 기본 몫을 무너뜨리거나 탐색 시간을 폭증시킬 수 있다. 새 승인 수동안이 없는 상태에서 계속 조정하면 일반 휴리스틱보다 `202608A` 전용 패턴을 학습할 위험이 크다.

## 9. 채택하지 않은 접근

- 수당 발생일 수를 환산 횟수로 간주하는 것
- 모든 회원에게 매일 수당을 강제하는 것
- 이름의 숫자·마커·조직 깊이를 우선순위로 쓰는 것
- PVP 목표 1,500·2,400 집단을 기본 몫보다 먼저 보는 것
- 점수 가중치만 반복해서 바꾸는 것
- beam 폭만 5에서 12 이상으로 늘리는 것
- Kelly 한 명의 900만 쪼개고 다른 기본 몫 손상을 무시하는 것
- 승인 수동안의 회원 이름·날짜·셀을 production에 하드코딩하는 것
- 베로니카 시작값 0 회귀를 235로 덮어쓰는 것
- 저장된 구버전 후보와 새 계산을 버전 확인 없이 비교하는 것
- 휴리스틱이 못 찾은 결과를 불가능 또는 최적이라고 표시하는 것
- 새 비교 채점기 없이 후보 생성기부터 다시 수정하는 것
- 새 gold가 없는 상태에서 달력상 4개월이 지났다는 이유만으로 Phase 4를 재개하는 것

## 10. 2차 동결 결정

2차 동결은 자동 계획이 완성됐다는 뜻이 아니다. 다음 네 가지가 확인된 안전한 중단점이라는 뜻이다.

1. 수동 계획표는 실제 업무에 사용할 수 있다.
2. V3는 모든 비루트 기본 몫을 지킨다.
3. V3는 승인 수동안이 더 좋다는 사실을 올바르게 평가한다.
4. 남은 한 회를 얻는 단순 Kelly 이동은 다른 회원의 몫을 빼앗으므로 production에 넣으면 퇴보다.

엄마가 브라질에 있는 약 4개월 동안 Phase 4를 억지로 계속 확장하지 않는다. 수동 계획표를 운영 기준으로 사용하고, 새로운 승인 수동안이 충분히 쌓인 뒤 공통 이동을 찾아 다시 연다.

**2026년 12월은 재개 기한이 아니라 최초 재검토 가능 시점이다.** 그때 J님의 업무가 가장 바쁜 상태이거나, 새 승인 수동안이 충분히 쌓이지 않았거나, 비교 채점기를 만들 여유가 없다면 2027년 이후로 그대로 미룬다. 새 증거가 없으면 4개월이 지나도 기술적으로 달라진 것이 없다.

## 11. 동결 상태를 Git에 보존하는 방법

V3 코드·테스트·문서를 `codex/phase4-v3-freeze-2026-08-04` branch와 annotated tag `phase4-v3-freeze-2026-08-04`로 보존한다.

### 11.1 권장 보존 구조

| 항목 | 권장 상태 |
| --- | --- |
| `main` | 현재 V2 및 공개 앱 기준 유지 |
| V3 | 별도 freeze branch에 커밋·푸시 |
| 불변 기준점 | 해당 commit에 annotated tag 추가 |
| 문서 | V3 코드·테스트와 같은 freeze commit에 포함 |
| 재개 | freeze tag에서 새 resume branch 생성 |
| 공개 배포 | 별도 검토 전까지 하지 않음 |

권장 이름은 다음과 같다.

```text
branch: codex/phase4-v3-freeze-2026-08-04
tag:    phase4-v3-freeze-2026-08-04
```

`main` push는 GitHub Pages 배포로 이어질 수 있으므로 V3 동결 보존만을 위해 `main`에 바로 병합하지 않는다.

### 11.2 같은 freeze commit에서 동기화할 자료

- `docs/requirements/pyramid-app-requirements-v2.md`
- `docs/CALCULATION_CASES.md`
- `docs/TECHNICAL_DESIGN.md`
- `docs/plans/PHASE_4_EXECUTION_PLAN_REVISED.md`
- `docs/ROADMAP.md`
- 이 인수인계 문서
- `src/optimizer/constants.ts`
- `src/optimizer/objective.ts`
- V3 후보 생성 관련 코드
- checkpoint 및 worker protocol 버전
- `src/optimizer/__tests__/202608a-gold-regression.test.ts`
- V3 objective pairwise tests
- 관련 개발 로그

특히 이전 정본 문서에 “좌·우 1,500 회원에게 별도 5회를 강제하지 않는다” 또는 PVP 목표 집단별 공평성 같은 V2 계약이 남아 있으면 V3와 충돌한다. freeze branch에서는 V3의 기본 몫 계약과 목적 순서를 코드·문서·테스트에 함께 반영한다.

`docs/ROADMAP.md`의 Phase 4 상태에는 다음 내용을 남긴다. GitHub Issue `#5`에 같은 내용을 연결하는 것은 별도 외부 기록 작업이며, branch/tag 동결의 필수 조건은 아니다.

- V3 2차 동결
- freeze branch·commit·tag
- 공개 앱은 V2 기준이라는 점
- V3는 평가기를 개선했지만 후보 생성 병목이 남았다는 점
- 재개 전 첫 산출물은 비교 채점기라는 점
- 이 인수인계 문서 경로

### 11.3 freeze 완료 체크리스트

1. V3 변경 전체를 검토한다.
2. 새 freeze branch를 만든다.
3. V3 코드·테스트·정본 문서·이 문서를 같은 branch에 모은다.
4. Section 4.2의 objective 세부사항이 코드와 pairwise test에 맞는지 확인한다.
5. Section 7.5의 자동 회귀와 일회성 diagnostic을 구분한다.
6. 전체 품질 검증을 실행한다.
7. `git diff --check`를 통과한다.
8. freeze commit을 만든다.
9. annotated tag를 만든다.
10. freeze branch와 tag를 원격에 push한다.
11. 실제 branch·tag와 기준 main commit을 이 문서 상단에 기록한다. 같은 commit 안에 자기 자신의 SHA를 넣을 수 없으므로 commit SHA는 tag 조회 명령으로 확인한다.
12. `main`에는 병합하거나 배포하지 않는다.
13. ROADMAP에 동결 상태를 연결한다. Issue `#5` 갱신은 명시적으로 승인된 별도 작업으로 남긴다.

freeze 완료 후 문서 상단 상태는 다음 형식으로 바꾼다.

```md
> 상태: V3 검증 완료 · 2차 동결 · 별도 freeze branch에 보존 · `main` 미병합 · 미배포
> V3 freeze branch: `codex/phase4-v3-freeze-2026-08-04`
> V3 freeze commit: `git rev-list -n 1 phase4-v3-freeze-2026-08-04`로 확인
> V3 freeze tag: `phase4-v3-freeze-2026-08-04`
```

## 12. Phase 4를 다시 여는 조건

다음 자료가 준비됐을 때만 큰 후보 탐색을 다시 검토한다.

- 서로 다른 기간 또는 조직에서 엄마가 만족한다고 확인한 승인 수동안 2~3개 이상
- 각 계획의 정확한 조직, 회원별 좌·우 목표, PVP 목표, 누적 PVP, 좌·우 시작값
- 자동 계산 직전의 불변 사본 또는 sanitized fixture
- 어떤 셀을 옮겼는지 알 수 있는 엄마 수정본
- Section 3.4의 gold 보존물
- 가능하면 빨강 `다시 계산할 곳`과 보라 `나중에 확인할 곳` 표시
- V1·V2·V3·승인 수동안을 같은 형식으로 비교할 수 있는 채점기
- freeze tag에서 재현한 기존 회귀 통과

엄마에게 일반 알고리즘을 말로 설명하게 할 필요는 없다. 같은 입력의 자동 사본과 엄마 수정본을 보존하면 코드로 날짜·회원·PVP·좌·우 차이를 추출할 수 있다. 다만 운영 중인 `사용중` 계획을 직접 수정하거나 이름만 같은 사본을 만들지 말고, 정확한 원본 ID 또는 export를 함께 보존해야 한다.

새 승인 수동안이 한 건도 늘지 않았다면 Phase 4를 재개하지 않는다. 그 상태에서는 새 휴리스틱이 일반 규칙인지 `202608A` 맞춤 규칙인지 판별할 수 없다.

## 13. 재개 후 첫 산출물: 계획 비교 채점기

다음에 만들 것은 새 알고리즘이 아니라 **계획 비교 채점기**다. 자동 후보 생성기나 production 목적함수를 다시 수정하기 전에, 같은 불변 입력에서 승인 수동안·V1·V2·V3를 동일한 평가기로 비교하는 리포트를 먼저 만든다.

채점기는 후보를 생성하지 않는다. 이미 존재하는 계획을 같은 기준으로 계산하고 차이를 설명한다. 평가기와 후보 생성기의 책임을 분리해, “좋은 계획을 판별하지 못하는 문제”와 “좋은 계획이 후보 집합에 없는 문제”를 따로 확인하는 것이 목적이다.

### 13.1 최소 출력 항목

- case ID
- 원본 snapshot/export ID
- request fingerprint
- algorithm version
- policy version
- objective version
- checkpoint version
- worker protocol version
- candidate/allocation fingerprint
- 회원별 PVP 목표
- 회원별 좌·우 보름 목표
- 회원별 기본 몫 목표
- 회원별 실제 수당 환산 횟수
- 회원별 기본 몫 부족 횟수
- 회원별 300·700·1,500·2,400 단계 발생 횟수
- 비루트 전체 환산 합계
- 맨 위 회원 목표 일수
- 맨 위 회원 실제 수당 발생일 수
- 맨 위 회원 미달 일수
- 총 신규 PV
- 구조상 최소 신규 PV `M`
- `M` 대비 초과량
- 확인 수당
- 소멸 초과 PV
- 마지막 carry
- 첫날 시작 잔액 대비 과다 투입 여부
- 자동안 대비 변경된 셀
- 각 변경 셀의 PVP·좌·우 증감
- 계획 간 objective 비교 결과
- 모든 보름 목표 충족 여부
- 모든 자동 입력값 계약 충족 여부

### 13.2 비교 대상

최소한 다음 계획을 같은 리포트 형식으로 비교한다.

1. Policy 8 baseline
2. V1
3. V2
4. V3
5. 승인 수동안
6. 새로 확보한 승인 수동안과 그 직전 자동안

### 13.3 채점기 완료 조건

- 같은 입력과 계획은 항상 같은 리포트를 만든다.
- 계산은 기존 Phase 1 엔진과 V3 평가기를 재사용한다.
- 회원별 결과가 aggregate 총액에 가려지지 않는다.
- 계획 간 셀 diff를 자동으로 출력한다.
- 시작값·조직·버전·fingerprint가 다른 계획은 같은 case로 조용히 비교하지 않는다.
- 여러 계획을 한 번에 나란히 비교할 수 있다.
- 채점기가 승인 수동안과 V3의 차이를 현재 회귀값대로 설명한다.
- 채점기가 완성되기 전에는 새 휴리스틱을 production 코드에 추가하지 않는다.

## 14. 재개할 때의 권장 실험 순서

1. **freeze 기준점에서 새 branch 만들기**
   `phase4-v3-freeze-2026-08-04` tag에서 resume branch를 만든다. 로컬 working tree의 기억에 의존하지 않는다.

2. **현재 상태 확인**
   `git status --short`, 현재 branch, commit, policy/objective/checkpoint/worker protocol을 확인한다.

3. **정본 문서와 코드 충돌 확인**
   이 문서, 계산 사례, 기술 설계, Phase 4 실행 계획, V3 objective tests를 완전히 읽는다. 충돌이 있으면 먼저 일치시킨다.

4. **기존 회귀 재실행**
   베로니카 시작값 0과 235 fixture가 모두 그대로 재현되는지 확인한다.

5. **계획 비교 채점기 구현**
   승인 수동안·V1·V2·V3를 동일한 리포트로 비교한다. 후보 생성기는 아직 수정하지 않는다.

6. **새 수동안을 같은 평가기로 측정**
   날짜별 셀을 답으로 하드코딩하기 전에 V3 comparator가 새 수동안을 자동안보다 좋다고 판별하는지 확인한다. 판별하지 못하면 평가 계약부터 다시 확인한다.

7. **좋은 후보가 후보 집합에 존재하는지 먼저 검사**
   점수 변경 전에 새 생성기가 승인 수동안과 같은 개선 방향의 후보를 실제로 만드는지 계측한다.

8. **다회원·다날짜 이웃을 작게 정의**
   한 회원의 다음 경계뿐 아니라 영향을 받는 조상·형제·기본 몫 손상 회원을 하나의 repair set으로 묶는다.

9. **탐색 예산을 명시한다**
   완전 탐색 대신 고정 seed, 최대 후보 수, 최대 반복 수, 실행 시간 상한을 둔다. diagnostic 결과에는 모두 기록한다.

10. **중간 악화를 제한적으로 허용한다**
    사람의 수정처럼 한두 단계 동안 점수가 나빠진 뒤 복구되는 경로를 허용하되, 기본 몫 훼손량과 repair budget을 명시적으로 제한한다.

11. **여러 fixture에서 같은 규칙을 검증한다**
    `202608A` 한 건에서만 좋아지는 이동은 채택하지 않는다. 최소 두 개의 독립 승인 수동안에서 공통 개선이 있어야 한다.

12. **production 변경 조건을 확인한다**
    모든 기본 몫, `M+30`, 총 PV, 보름 목표, 결정성, 실행 시간을 지키면서 비루트 합계 또는 승인 수동안 대비 간극을 실제로 줄일 때만 새 policy로 올린다.

13. **버전과 저장 호환성을 함께 올린다**
    policy/objective 변경과 checkpoint/worker protocol 호환성 변경을 함께 검토한다. 구버전 후보가 새 평가 결과로 조용히 복원되지 않게 한다.

14. **문서·테스트·Issue를 같은 변경에서 갱신한다**
    코드만 바꾸고 인수인계 문서를 나중에 맞추지 않는다.

## 15. 재개 시 바로 볼 파일과 명령
